## 任务执行规则

```yaml
执行规则:
  1. 每个任务执行前输出确认信息，等待用户回复
  2. 每个任务完成后必须经过两轮测试验证
  3. 复杂功能必须先输出开发计划，等待用户确认
  4. 每个任务完成后立即停止，等待用户确认
  5. 禁止跨任务编码、禁止推测用户意图
  6. 自动化测试默认使用Mock；仅管理员或用户明确授权的连接测试、目标部署验收允许一次不携带业务数据的短调用，禁止自动重试和无授权计费调用
  7. 所有LLM调用必须包含重试和降级机制
  8. 基于正常社会思维和人类使用逻辑进行开发
  9. 任务ID保持稳定；当新增任务形成前置依赖时，依赖关系优先于编号顺序
  10. 🟦 每个业务模块必须按“后端能力→对应前端→前后端联调→用户验收”纵向闭环，未完成可视化验收不得进入下一个业务模块
  11. 🟪 决策者一次性确认5个或以上任务时，编码前必须全量审查此前所有前后端功能；每累计完成5个任务必须通过兼容性审查和全量测试并创建Git提交及附注标签
 12. HTTP 200/201 或页面可打开不等于功能通过；必须同时完成业务断言、浏览器 Console/Network 监控、边界/权限/失败恢复/幂等测试，所有情况通过且无未解释错误后才能标记完成
```

## 模型使用路由与功能选择整改计划（已审核，按任务执行）

> 本计划对应 `PRD_V5.0.md` 第13.4节，是新增整改任务。审核通过前不编码、不标记任务完成、不修改既有任务统计；整改不追溯性否定此前已完成并验收的功能，历史差异通过本计划或独立补漏任务兼容处理。审核通过后仍须一次只执行一个任务，并按“后端模型/服务 → REST API → 对应前端 → 真实本地API联调 → 用户验收”闭环。

### 整改目标与统一规则

- 模型选择优先级统一为：本次操作临时选择 → 功能已保存绑定 → 平台全局默认 → 明确启用的备用模型 → 用户明确选择的确定性基线。

- 全局默认模型必须经过能力过滤；不支持视觉、结构化输出或长上下文的模型不得被强行用于对应功能。
- “未配置”“能力不匹配”“供应商/密钥/网络调用失败”“使用备用模型”“使用确定性基线”必须分别展示并写入审计；默认不允许静默降级。
- 每个功能都提供“继承全局”选项，并展示最终生效的供应商、模型、能力和来源；临时选择不覆盖已保存配置。
- 每个任务完成后执行专项测试和全量/集成测试，更新 `PROJECT_STATUS.md`；发现历史遗漏、权限、兼容性或状态不一致时先记录影响和整改顺序。

## 🟩 阶段24：RAG 二阶段——知识增强检索与智能体引用

> 本阶段是下一阶段的规划草案，需决策者审核后再编码。它用于补齐历史 T108（LlamaIndex 适配）和 T025（pgvector/关键词混合检索）的架构差异，不追溯性否定已验收的知识库 CRUD、解析和基础检索能力。阶段内仍必须逐任务执行，并遵守“后端能力 → REST API → 对应前端 → 真实本地 API 联调 → 用户验收”的纵向闭环。

### 阶段目标与明确边界

- 目标：把现有知识库基础能力升级为可解释、可评估、可回退、严格项目隔离的 RAG 能力。
- 数据真理源：Django ORM、PostgreSQL、审核状态和项目权限；LlamaIndex 只能作为文档节点、索引和检索适配层。
- 检索底座：PostgreSQL 16 + pgvector + PostgreSQL 全文关键词检索；不新增独立向量数据库。
- 默认产品路径：审核通过 → 建立索引 → 混合召回 → 去重/融合 → 可选重排序 → 引用上下文 → 智能体回答。
- 明确不做：本阶段不引入 MCP、多智能体框架、第二套主编排器、自动训练模型或无审计的自动知识沉淀。
- 兼容策略：保留旧 JSON 向量读取和离线 HashVectorizer 作为测试/迁移工具，但不得在生产路径无提示地冒充真实 RAG。
