## 1. 产品概述

### 1.1 产品定义

AI智能体测试平台是一个**对话驱动的智能测试助手**。用户通过自然语言描述测试需求，平台智能体自主完成需求分析、用例生成、测试执行、结果分析、报告推送全流程。

### 1.2 核心差异化

- **对话即测试**：自然语言交互，无需编写测试代码
- **需求深度分析**：上传/导入需求文档，LLM深度理解并拆解功能
- **联合功能识别**：自动识别跨模块联动场景（功能A在功能C页面展示）
- **用例智能生成**：多轮对比确认，自动评审，自动筛选自动化用例
- **业务联调测试**：不仅测单接口，自动识别并测试业务链路
- **多类型测试**：接口/UI/APP/性能/AI/安全/回归/数据，共9种
- **多模型兼容**：OpenAI/Claude/Gemini/通义千问/DeepSeek等
- **四级提示词**：即时>场景>项目>全局，默认预置
- **知识持续沉淀**：含人工审核，使用越多越智能
- **主动测试建议**：Git变更/质量趋势/环境异常主动通知
- **多渠道通知**：企业微信/钉钉/邮件/平台内消息
- **测试资产复用**：用例模板、策略模板、缺陷模式跨项目复用
- **效果可度量**：ROI仪表盘、时间节省量化

#### 🟪 F1.2 上下文记忆二期预留

上下文记忆属于二期智能体底座能力，不要求一期核心测试闭环延期，但必须按以下五层逐步建设，避免把“把历史消息拼进 Prompt”误认为完整记忆系统：

1. **短期对话记忆**：保存当前会话消息、当前任务状态和最近上下文；支持长度预算、摘要、去重和敏感信息过滤。
2. **会话恢复**：用户可以从历史会话继续任务；恢复前重新校验用户、项目、角色和数据权限，避免恢复已失效或越权的上下文。
3. **项目记忆**：保存项目级的已确认需求、测试决策、环境约束、用例资产和用户确认结果；项目成员只能访问其有权限的内容。
4. **长期知识记忆**：将经过审核的项目知识、历史结论和测试经验建立可检索记忆，并显示来源、时间、版本和引用；未审核内容不得自动成为事实。
5. **个性化偏好记忆**：在用户明确知情和允许的前提下保存语言、展示、测试习惯等偏好；支持查看、修改、清除和停用。

记忆底座统一由 LangGraph 主编排器调用 `MemoryService` 和 `ContextAssembler`，不新增第二套智能体主编排框架。所有记忆必须具备范围隔离、生命周期/过期策略、删除能力、审计记录、脱敏处理和上下文预算；记忆召回失败时必须明确提示，不能静默伪造或跨项目拼接上下文。

### 5.3 打断处理（三模式）

| 打断类型       | 用户表达             | 智能体行为   | 结果处理         |
| -------------- | -------------------- | ------------ | ---------------- |
| 暂停（Pause）  | "等一下"、"暂停"     | 保留中间状态 | 补充信息后可继续 |
| 停止（Stop）   | "停止"、"不要执行了" | 停止当前执行 | 保留已完成结果   |
| 取消（Cancel） | "取消"、"算了"       | 取消当前执行 | 清理临时数据     |

**响应要求**：用户在对话中输入打断指令，智能体≤3秒响应，不等待当前任务完成。

#### F4.1.2.A 五轮递进需求分析语义【V5.4 已评审】

需求深度分析的“五轮”是对同一份需求进行递进式复核，不是把需求切成五段，也不是无目标地重复五次。每一轮都必须在前一轮累计结果的基础上寻找遗漏、补充测试点或修正错误；最终只保留一份经过五轮合并、去重和证据校验的分析结果。

| 轮次 | 分析重点 | 必须完成的工作 |
| ---- | -------- | -------------- |
| 第 1 轮 | 基础拆解 | 从完整需求和解析证据提取功能模块、功能点、业务流程、初始测试点和证据引用 |
| 第 2 轮 | 异常与风险补全 | 重新对照完整需求，检查异常、权限、输入校验、依赖失败、网络失败和安全场景遗漏 |
| 第 3 轮 | 边界与状态补全 | 检查边界值、空值、重复提交、状态切换、并发、恢复、重试和数据一致性场景遗漏 |
| 第 4 轮 | 关系与联动补全 | 检查模块关系、数据流、接口契约、状态联动、跨模块流程和联合测试点遗漏 |
| 第 5 轮 | 最终质量复核 | 检查证据覆盖、归属关系、测试类型、重复项、冲突项和高风险遗漏，形成最终审核输入 |

每一轮的输入必须包括完整需求正文、全部解析证据、前轮累计模块/功能点/联合场景/测试点、已覆盖证据、未覆盖证据和前轮问题清单。第 2～5 轮不得只读取上一轮新增内容，避免遗漏原文中的其他上下文。

每一轮的输出必须区分 `added`、`updated`、`duplicate`、`conflict` 和 `uncovered_evidence`，并记录轮次重点、实际模型、调用分段、耗时、失败原因、本轮新增数和累计数。模型只允许输出有原文证据支撑的模块、功能点和测试点，不得为了达到覆盖率虚构内容。

“轮次”与“分段”必须独立计数：轮次表示语义复核次数，分段表示单轮因上下文或输出预算进行的技术切分。页面不得把“分段 5/5”显示为“五轮分析完成”；成功状态必须明确表示“五轮均完成”。

五轮完成后仍须经过人工审核。人工审核对象是最终测试点及其模块、功能点、描述、测试类型和原文依据；用户可以逐项或批量勾选测试点并标记为“已审核”，已审核测试点进入独立集合并可在用例生成页选择对应范围生成用例。证据未覆盖、结构归属缺失、类型缺失、冲突未处理或任一轮失败时，不能完成最终分析确认；未完成最终确认时也只能生成已明确标记为已审核的测试点，不能消费未审核结果。

#### F4.1.2.B 跨运行分析稳定性、权威快照与差异审核

同一份需求文档、接口文档、UI/App 流程或性能资料重复分析时，重新运行不是对旧结果的静默覆盖，而是对当前权威版本的候选修订。相同来源指纹、解析证据版本和同一功能配置下，平台必须识别为同一业务对象的后续分析，并保留历史运行、当前权威快照和本次候选结果。

平台必须将分析结果分为以下层次：

1. **分析运行：** 记录输入资料/证据版本、模型/提示词/Skill/配置快照、运行 ID、状态、调用轮次、失败和重试。
2. **候选结果：** 保存本次模型或规则分析的完整结构化输出及其来源，不得直接成为下游输入。
3. **权威分析快照：** 只有通过稳定性门禁并完成人工确认的结果才能成为当前权威版本；评审、拆解、测试点和用例等下游必须引用明确的快照 ID/版本，禁止读取“最新分析”。
4. **审核决策：** 决策必须绑定平台生成的稳定对象 ID 和快照版本，不能绑定会随模型输出顺序变化的临时 ID。

分析对象的稳定身份必须优先依据原文证据 ID、原文位置/内容指纹、父级对象、业务类型、规范化语义和测试类型生成。模型返回的对象 ID、名称措辞和输出顺序只能作为候选信息，不能单独决定“新增”“删除”或“同一对象”。解析证据 ID 在同一来源版本内必须稳定；文档内容发生变化时必须生成新来源版本并记录影响范围。

每次候选结果与当前权威快照比较时，必须明确分类为：保持不变、仅文字变化、新增候选、疑似删除、父级关系变化、测试类型变化、证据变化、语义冲突、重复对象或无法自动关联。模型本次没有输出不等于原对象可以删除；已确认对象只能进入“疑似删除/待确认”，不能静默消失。冲突必须同时保留权威值、候选值、原文证据、来源运行、模型/版本和影响下游。

稳定性门禁至少包括：

- 已确认对象被删除、换父级、失去证据或测试类型改变时阻断自动发布。
- 证据覆盖率下降、关键流程断裂、模块/功能点/测试点关系不完整或候选结果无法唯一关联时进入 `unstable`/`needs_review`，不能覆盖权威快照。
- 同一资料、同一配置和同一模型的重复运行出现非文字性的结构变化时必须生成跨运行差异报告；数量下降只能作为风险信号，不能作为唯一判断依据。
- 不同模型、不同提示词、不同配置或不同执行器的结果一律先作为候选版本；不得以“最后一次结果”或“数量最多的结果”自动判定正确。
- 只有候选结果通过 Schema、来源证据、结构关系、稳定性和人工审核门禁后，才可创建新的权威快照并使明确受影响的下游版本失效。

用户界面必须展示当前权威版本、本次候选版本、差异类型、原文依据、影响范围和决策入口。人工操作不能只有“已查看/已勾选”，至少应支持保留旧值、采用新值、合并、标记重复、确认删除、驳回和暂不决定；已审核且未发生语义变化的对象应自动继承审核状态，只有新增或受影响对象进入待审核。

分析、需求评审、测试点拆解、用例生成以及接口/UI/App/性能测试资产生成，均必须消费冻结的上游权威快照。重新分析不得让下游在执行中改读新版本；上游产生新权威快照后，按血缘精确标记受影响节点为待复核或失效。模型随机性可以产生候选差异，但不能改变当前权威结果、人工审核集合或已发布测试资产的来源关系。

### 11.5 Skills扩展与第三方兼容

平台必须同时支持内置 Skill、项目自定义 Skill 和经审核的第三方 Skill。自定义 Skill 不能只保存配置，必须能够绑定受控运行时实现，并经过输入输出契约校验后由智能体调用。

第三方 Skill 来源至少兼容本地 Skill 包、GitHub 仓库、SkillHub 地址和可下载的版本化包。所有来源必须记录来源地址、版本、提交哈希或文件哈希、作者、许可证、安装人、审核人和安装状态；禁止未审核代码直接执行。

第三方 Skill 安装必须经过管理员审批，支持版本锁定、启用/停用、卸载和回滚。Skill 必须声明网络、文件、数据库、外部命令、模型、知识库和环境凭据权限，默认拒绝高风险权限；运行时必须执行项目隔离、超时、资源限制、错误隔离和审计记录。

第三方来源不可用、内容校验失败、权限超出审批范围或运行时异常时，平台必须安全失败，并保留内置 Skill 和已批准本地 Skill 的正常使用能力。Skill 来源适配、安装和运行权限必须通过平台前端可见、可审计、可撤销。

### 11.6 Skill分层配置与跨功能质量闭环（新增需求，已完成自审，待决策者评审）

#### 11.6.1 需求目标

Skills不能只作为独立的注册、启停或执行状态展示，也不能在业务接口完成后以旁路方式补充一次“Skill已调用”标记。需求分析、测试点审核、用例生成、用例评审和人工评审必须使用可配置、可追踪、可联动的Skill链路；上游Skill的真实结构化结果必须成为下游Skill的输入，任何一个环节缺失、失败、过期或未完成审核，都不得静默进入下一个环节。

平台必须同时满足以下要求：

1. 用户或管理员可以配置全局默认Skill，并针对具体项目、具体业务功能和当前一次操作进行覆盖。
2. 业务页面必须能够选择、查看和确认本次实际使用的Skill；系统必须展示继承来源、Skill名称、版本、配置快照和执行状态。
3. 核心Skill必须按业务意图强制绑定，关联Skill可以由系统推荐，但在进入高风险或产生持久化测试资产前必须经过用户确认或符合已配置的自动确认策略。
4. 每次Skill执行必须保留输入产物、输出产物、上游版本、下游关联、配置解析结果、执行状态、失败原因和重试记录。
5. 同步请求、异步任务、页面操作、MCP调用和智能体调用必须复用同一套Skill解析、执行、审计和错误契约，不能因入口不同而绕过Skill配置。

#### 11.6.2 Skill配置层级与解析规则

Skill配置至少支持以下层级，优先级从高到低为：

1. 即时指定：用户在当前需求分析、需求评审、需求拆解、测试点拆解、测试点评审、用例编写或用例评审操作中明确选择的Skill及版本。
2. 功能级：针对需求分析、需求评审、需求拆解、测试点拆解、测试点评审、用例编写、用例评审、人工评审等具体业务功能绑定的Skill及版本。
3. 项目级：针对某个项目的默认Skill链、允许使用范围、版本锁定和覆盖规则。
4. 全局默认：平台管理员配置的默认Skill链和安全策略。

解析规则必须满足：

- 高层配置覆盖低层同一功能的配置；未覆盖字段由低层补充。
- 核心Skill只能有一个最终生效版本；关联Skill可配置为有序列表，并保留推荐理由。
- 禁用、撤销、未审核、版本不兼容或权限不足的Skill不得被静默替换为其他Skill；必须返回可解释的阻断状态和处理入口。
- 操作开始后必须锁定本次配置快照和Skill版本，执行过程中不能因后台配置变化而改变本次结果。
- 旧记录必须能够读取历史Skill名称、版本和配置快照；升级Skill不能覆盖既有执行证据。

#### 11.6.2.1 Skill安装记录、能力库与真实执行状态

- **安装记录**负责来源、版本/提交或文件哈希、作者与许可证、审批人、安装人、权限审批以及启用、停用、卸载和回滚等来源与生命周期证据；**Skills能力库**负责保存平台标准化后的单项能力定义、展示名称、版本、输入/输出契约和受控适配器信息。两者职责分开，安装记录不能替代能力定义，能力定义也不能替代安装来源和审批证据。
- 安装校验通过后，平台必须自动把安装记录与发现的能力库条目关联，并由平台生成稳定的 `skill_id`。同一可信来源、稳定包身份和包内能力路径/身份的升级应沿用该能力标识并保留版本历史；不同来源的同名能力应分别保留，不能静默覆盖。身份缺失或冲突时由管理员处理，不得要求普通用户手工填写标识或建立关联。
- `skill_id` 是平台内部引用，不是普通用户的配置输入。普通用户必须通过能力显示名称（必要时同时显示来源与版本以区分同名项）查找和选择 Skill；工作台与 API 封装不得要求其手写 UUID、原始 JSON 或内部权限字段。
- 产品状态必须区分“已安装”和“运行就绪”。“已安装”表示来源/完整性校验与审批通过、制品仍由平台管理且未卸载或撤销；是否启用单独展示。“运行就绪”还要求该版本已启用、有受支持的适配器、元数据与输入/输出契约校验通过、所需依赖和权限可用，并通过当前运行环境的执行预检。已安装不代表运行就绪；依赖、权限、适配器或运行环境变化后必须重新评估就绪状态并给出阻断原因。
- 仅有计划、占位回显、Mock/Dry-run 或安装成功记录，不构成真实能力执行，不得展示为 Skill 执行成功，不得作为真实结构化产物推进下游业务。真实成功必须有指定安装来源及版本的运行时执行证据、经过契约校验的实际输出，并记录其被哪个下游节点消费；没有可用适配器时应显示未就绪/受阻，不得伪造输出。
- 卸载、撤销审批、哈希不符或权限撤回必须立即撤销当前可运行关联并阻断后续调用，同时保留安装与历史执行审计；不能静默切换到另一个同名来源或版本。

#### 11.6.3 核心业务Skill链

平台必须实现以下最小闭环，并允许未来扩展其他测试能力：

需求文档解析
    ↓

    ↓ 输出：需求摘要、来源证据、模块候选、风险和分析版本

    ↓ 仅已审核测试点可进入下游

    ↓ 输出：可执行用例、测试设计方法、需求/功能点/测试点追踪关系
用例评审 Skill
    ↓ 输出：覆盖率、重复度、边界、可执行性、风险和问题清单
人工评审用例
    ↓ 人工确认、修订或新增；修改后必须重新触发受影响的自动评审
最终用例集

各环节必须满足以下业务契约：

1. 需求分析 Skill：输入必须包含需求原文、解析证据和需求文档版本；输出必须包含结构化需求摘要、模块/功能候选、证据ID、风险和分析版本。输出必须标识质量状态。
2. 需求评审 Skill：输入必须包含需求分析版本、分析结果、证据覆盖和风险信息；必须评审完整性、结构归属、证据充分性、风险遗漏、跨模块关系和版本变化，并输出可定位结论。需求评审未完成或阻断时，不得进入需求拆解和后续步骤。
3. 需求拆解 Skill：输入必须包含通过需求评审的版本和证据；输出模块、功能点、业务流程、数据对象、验收条件及其需求来源关系。每项拆解必须可回溯，不能只按标题扩写。
4. 测试点拆解 Skill：输入必须包含通过评审的需求拆解版本、功能点、证据和测试约束；输出覆盖正常、边界、异常、安全、权限、并发、恢复等适用维度的测试点及来源追踪。空范围、证据不足或Schema错误时必须明确阻断。
5. 测试点评审 Skill：输入必须包含需求评审/拆解版本、测试点集合、证据引用和配置快照；必须校验归属、描述、测试类型、证据支持、重复和冲突，并输出逐项结论。未通过或待确认的测试点不得自动进入用例生成集合。
6. 人工评审测试点：提供逐条确认、修改、驳回和意见入口；只有已确认集合进入用例编写。
7. 用例编写 Skill（用例生成）：输入必须包含已确认测试点ID集合、需求评审版本、生成Skill版本和测试设计约束；每条用例必须反向追踪到功能点、测试点和证据，禁止只依据需求标题生成不可追踪用例。
8. 用例评审 Skill：输入必须包含用例集版本、上游审核版本和需求追踪关系；必须输出覆盖率、重复度、边界/异常/安全/权限等维度的问题、严重级别、证据和修订建议，并明确评审结论。
9. 人工评审用例：无论用例评审Skill通过或不通过，都必须提供独立人工入口。人工评审可以逐条确认、修改、删除或新增用例；修改或新增后，受影响的自动评审和自动化筛选结果必须失效并重新评审。
10. 任何上游版本变化都必须标记下游产物为待复核或失效；旧版本结果不得显示为当前链路已完成。

#### 11.6.3.1 各业务域独立总运行、唯一结果与动态进度强制要求

上述 Skill 链路不是只针对“需求文档 → 用例”的一条固定流程，而是所有 Skill 驱动测试功能的共同执行契约。输入可以是需求文档、接口文档/OpenAPI、页面原型或 UI 流程、App 交互说明或安装包、性能目标/SLO/压测方案、已有测试用例、日志以及其他经平台认可的测试资料；不同输入对应不同业务域、Skill 链、执行器和结构化产物。

平台共享的是运行协议、状态机、快照、血缘、进度投影和失败恢复能力，不共享一个会混合所有领域的默认总运行。每个业务域和功能页面必须拥有自己的工作流父级总运行：

```text
需求分析页面   → 需求分析域父级总运行
接口自动化页面 → 接口自动化域父级总运行
UI 自动化页面  → UI 自动化域父级总运行
App 自动化页面 → App 自动化域父级总运行
性能测试页面   → 性能测试域父级总运行
```

接口自动化的节点只能进入接口自动化父级运行，UI、App、性能和需求分析同理。不同业务域不能因为共用 Skill 运行底层、项目、模型或进度组件，就把节点、输入、输出或百分比混在一起。只有用户明确发起跨域编排时，平台才可以创建一个明确标注范围的上层编排运行或受控父子运行；跨域运行必须声明参与的业务域、来源产物和边界，不能作为任何单一业务域页面的默认运行。

每个业务域父级总运行在第一个业务节点执行前必须冻结并持久化：

1. `workflow_key`、业务域、功能入口、输入资料类型、资料/环境版本、输入内容指纹和项目/操作者范围。
2. 生效 Skill 链版本、每个节点唯一 `node_id`、Skill 名称与版本、领域执行器、节点顺序、依赖、人工门禁和失败策略。
3. 全局/项目/功能/本次指定的配置解析结果，以及模型、提示词、知识库、工具、浏览器/设备/接口环境、外发和成本策略快照。
4. 幂等键、父级运行 ID、执行计划版本和本次运行的来源血缘范围。

每个节点必须满足“一次运行、一个明确身份、一个明确输入版本、一个明确输出版本”的关联规则：

- 每个节点只能绑定到当前业务域父级运行内的一个确定 Skill 版本、执行器和配置快照；缺失、禁用、未审核、未就绪、权限不足、环境不满足或版本不兼容时必须在执行前阻断。
- 节点输入必须引用当前父级运行中已经验证的上游产物 ID、版本和指纹；禁止按“最新记录”或标题重新查询，禁止跨业务域父级运行拼接结果。
- 节点输出必须先以带版本和指纹的结构化产物持久化，并通过 Schema、来源证据、领域执行器结果、环境/授权检查和业务质量门禁，之后才能标记节点完成并解锁下游。
- 节点、Skill、输入、输出、执行器、环境、配置或来源证据出现重复、缺失、歧义或无法唯一关联时，必须阻断并给出定位信息，不能猜测、覆盖或静默选择一个结果。

父级与节点必须使用通用但相互隔离的状态机，至少区分计划、排队、执行中、等待人工、已复用、不适用、已完成、阻断、失败、取消中、已取消、超时和重试中。只有当前业务域内所有适用的必需节点真实产物已经校验并持久化、人工门禁已通过、且没有未解释的错误或过期上游时，该业务域父级运行才能完成；其他业务域成功不能替代本业务域缺失的节点。

“唯一正确的结果”在平台中定义为：**同一个业务域、同一个冻结父级总运行内，唯一可追溯、不可混用、经过全部门禁的权威结果版本**。这不宣称模型或测试执行不会产生需要人工判断的不同答案；系统必须保证不同业务域、不同运行、不同资料版本、不同 Skill、不同执行器、不同环境或不同配置的结果不能被拼成一个看似完整的结果。明确重试或重新执行必须创建新的尝试/父级运行并保留旧运行证据，不能覆盖旧结果或改变旧运行的血缘。

动态进度必须来自当前业务域父级运行的持久化快照和有序事件，而不是前端计时器或模型文本推测：

- 业务域页面展示自己的总链路、当前节点/总节点、当前 Skill 与版本、领域执行器、阶段提示、可验证工作量、等待原因、失败原因和重试入口。
- 百分比只计算当前业务域本次运行实际适用且必需节点的已完成权重和当前节点可证明的工作量；其他业务域运行、跨域来源产物和被复用的有效上游单独显示，不能计入当前页面的执行百分比。
- 没有可靠节点内计量时只在阶段边界推进，不能按时间匀速增长；未完成当前业务域必需节点、未通过人工门禁或存在阻断时不得到达 100%。
- 页面刷新、重复点击、断线恢复、取消和重试必须读取同一业务域父级运行及其事件序号；关闭弹窗只隐藏视图，不能取消后台运行。

需求分析、接口自动化、UI 自动化、App 自动化、性能测试和未来新增领域必须只声明自己的输入契约、Skill 节点、执行器和真实工作量，不能各自复制一套进度算法或结果关联逻辑。页面、REST、Celery、智能体和 MCP 必须调用同一套运行协议，但必须传入明确的业务域和 `workflow_key`；任何入口不得跳过本业务域父级运行、直接调用下游 Service、重新查询最新记录或把计划/占位/Mock/Dry-run 当成真实完成。

#### 11.6.4 业务页面与用户操作要求

需求分析工作台必须提供：

- 当前生效Skill链查看、功能级Skill选择、全局/项目继承提示和本次临时覆盖入口。
- 需求分析Skill执行轨迹、输出版本、证据覆盖和失败/重试状态。
- 需求评审Skill、需求拆解Skill、测试点拆解Skill和测试点评审Skill的结果展示，以及逐项人工审核、确认、驳回和重新分析入口。
- 当前执行链路、真实进度百分比、当前阶段/总阶段数、当前Skill及阶段对应的动态过程提示；刷新页面后可恢复同一执行记录。
- 明确的“已审核测试点”集合，并将该集合作为用例生成页面的唯一可生成范围。

用例生成工作台必须提供：

- 用例生成Skill选择、继承来源、生效版本和配置快照。
- 生成结果到需求分析版本、功能点、测试点和证据的追踪展示。
- 用例评审Skill选择、评审报告、问题定位和重新评审入口。
- 独立的“人工评审”入口，不得使用“无需人工评审”替代人工评审状态。
- 人工评审范围至少包括评审问题用例、待评审用例、全部用例和新增用例；保存后必须显示待重新评审状态。

Skill管理工作台必须提供：

- 全局默认Skill链配置。
- 功能级Skill绑定和覆盖配置，至少覆盖需求分析、需求评审、需求拆解、测试点拆解、测试点评审、用例编写、用例评审和人工评审辅助。
- 项目级Skill覆盖、版本锁定、启停和回滚。
- 配置冲突、缺失、权限不足、版本不兼容和执行失败的可解释反馈。
- 配置生效预览，能够展示“全局默认 → 项目级 → 功能级 → 本次指定”的解析结果。

#### 11.6.5 联动、状态与数据一致性要求

每个业务产物必须携带并持久化以下关联信息：

- 上游产物类型、ID、版本和内容指纹。
- 实际使用的Skill名称、ID、版本和配置层级。
- Skill输入摘要、输出摘要、执行状态、耗时、错误码和重试次数。
- 下游可用状态：可继续、待人工审核、待重新评审、已失效、已完成或已阻断。
- 人工操作人、操作时间、修改前后差异和审核结论。

状态流转必须满足：

```text
待分析 → 分析完成 → 需求待评审 → 需求已评审 → 需求拆解完成
→ 测试点拆解完成 → 测试点待评审 → 测试点已审核
→ 用例编写完成 → 自动评审完成 → 人工评审中
→ 待重新评审（如有修改） → 最终用例集
```

系统不得出现以下情况：

- Skill执行成功但其输出未被业务主流程消费。
- 页面显示Skill已完成，但异步任务未实际执行该Skill。
- 自动评审通过后隐藏或禁用人工评审入口。
- 人工修改后仍保留旧的自动评审通过、自动化筛选或最终确认状态。
- 需求分析、需求评审、测试点评审、用例生成和用例评审使用不同版本却没有阻断或提示。
- Skill失败时静默降级到未配置、旧版本或确定性结果并伪装为成功。

#### 11.6.6 权限、安全与失败恢复

- 全局配置仅平台管理员可修改；项目级配置由项目所有者/管理员管理；普通成员根据项目权限只读或按授权选择。
- 即时指定Skill不得突破项目范围、安装审批、权限声明、版本锁定和模型/知识库外发策略。
- Skill执行失败、超时、断连、输入字段错误、401、403、服务不可用和版本不兼容必须提供明确错误码、重试入口和当前产物状态。
- 重试必须从可恢复检查点继续，不得重复写入相同版本产物，不得重复产生未提示的外部费用。
- 日志和审计必须脱敏，不得记录密钥、令牌、完整需求原文或未经授权的跨项目数据。

#### 11.6.7 MCP与真实联调要求

该需求完成前必须通过MCP对业务页面和真实本地API进行闭环验证，不能只验证接口返回结构。至少覆盖：

1. 全局默认Skill生效。
2. 项目级Skill覆盖全局默认。
3. 功能级Skill覆盖项目级配置。
4. 当前操作临时指定Skill并在执行证据中锁定版本。
5. 需求分析→需求评审→需求拆解→测试点拆解→测试点评审→人工确认→用例编写→用例评审→人工评审的真实联动。
6. 正常、空数据、字段错误、401、403、Skill停用、版本冲突、Skill失败、任务取消、超时、重试和旧数据兼容。
7. 修改需求分析、测试点或用例后，下游状态正确失效并可重新执行。
8. 同步执行和Celery异步执行产生一致的Skill配置快照、执行记录和最终状态。
9. 安装记录与能力库条目自动关联，`skill_id` 由平台生成；普通用户通过名称选择，不手写 UUID/JSON。
10. 分别验证“已安装”和“运行就绪”；没有真实运行证据的计划/占位/Mock/Dry-run 输出不能成为成功结果或下游输入。

#### 11.6.8 验收门禁

该需求不得以“Skill列表可见”“接口返回skill_execution”或“页面显示自动调用Skill”作为完成标准。只有同时满足以下条件才允许验收通过：

- 所有核心业务功能均有全局默认、项目级、功能级和即时指定的配置解析证据。
- 所有上游输出均被下游真实消费，并能通过ID、版本和指纹反向追踪。
- 需求评审、需求拆解、测试点拆解、测试点评审、用例编写、用例评审和人工评审均有独立入口和持久化状态。
- 自动评审与人工评审状态完全分离，人工评审永远可进入且修改后能触发重新评审。
- 同步、异步、页面、MCP和智能体入口使用同一业务闭环。
- 影响范围内的后端专项测试、前端构建、真实本地API、MCP多维度联调和回归测试全部通过。
- 失败、阻断、权限不足或配置缺失时不产生伪成功结果，并保留可恢复路径。
- 安装记录与能力库分工清楚且由平台自动关联；名称选择、平台生成标识和同名来源冲突处理均有真实界面/API 证据。
- “已安装”与“运行就绪”状态分离；计划、占位、Mock 或 Dry-run 不得伪装成真实运行，也不得推进业务链。

#### 11.6.9 关键设计判断与不可混用边界

本需求不把“Skill被调用”直接等同于“业务结果正确”，必须明确以下职责边界：

1. Skill负责声明能力、编排步骤、生成或校验结构化结果；业务Service负责领域规则、权限、版本门禁、持久化和事务一致性。Skill不得绕过业务Service直接写入最终需求、用例、执行记录或报告。
2. 需求评审Skill、测试点评审Skill、用例评审Skill即使底层复用同一个模型或运行时，也必须是不同的业务节点、输入输出契约和审核状态，不能用一个“评审完成”字段覆盖多个门禁。
3. 人工评审不是大模型评审的别名，也不是只有发生修改时才存在。无论自动评审通过、未通过、未发现问题还是自动评审未执行，只要存在可审核用例，就必须能够进入人工评审并明确确认“已人工审核”。
4. “关联Skill推荐”不能自动获得核心Skill的权限。推荐Skill只有在用户确认或符合已配置的低风险自动确认策略后才能执行；写入、外发、执行测试、修改环境或产生费用的操作必须单独经过授权。
5. Skill可以是确定性、模型辅助或外部工具型，但必须声明执行模式。计划型Skill只能报告为“计划已生成”，不能伪装为已完成需求分析、已生成用例或已完成评审；只有其输出被后续业务节点消费后，业务链路才可推进。
6. 确定性基线、旧逻辑兼容和降级结果必须显式标注来源与可信等级，不能把“接口成功”“返回JSON”或“兜底结果存在”当作模型或Skill验证成功。

#### 11.6.10 端到端产物、契约和下游消费矩阵

每个节点必须有明确的输入、输出、责任方和下游门禁。下表中的“输出”必须真实持久化并被下一节点消费，不能只写入展示字段。

| 节点 | 必需输入 | 必需输出 | 放行条件 | 直接下游 |
| --- | --- | --- | --- | --- |

#### 11.6.11 Skill链编排运行时要求

Skill配置不能只保存一个Skill ID列表，必须保存可执行的链配置。每条链至少包含：

- 节点ID、节点类型、核心/关联标识、Skill ID、版本或版本范围、执行模式和输入输出Schema。
- 节点依赖、执行顺序、可并行分支、汇聚规则、人工门禁和失败策略。
- 超时、重试、取消、断点恢复、幂等键、并发锁和最大成本/调用次数。
- 允许的模型、提示词、知识库、环境、MCP工具和外发数据范围。
- 兼容性规则：哪些上游字段或版本变化会使当前节点及其下游失效。

运行时必须满足：

1. 同一业务操作只能产生一个可识别的执行实例；重复提交必须返回已有实例或安全拒绝，不能重复生成资产或重复产生外部费用。
2. 任务取消必须记录取消请求、实际停止点和已产生的部分结果；部分结果不能标记为完整成功。
3. 失败重试必须从最近一个已提交且可验证的节点恢复；已完成节点不得无提示重复执行，除非用户明确选择重新运行。
4. 多个关联Skill并行执行时，汇聚节点必须等待必需节点完成，并记录缺失的可选节点；不能因一个推荐节点失败而伪造整个链路成功。
5. 配置、模型、提示词、知识库、Skill和输入产物在执行开始时形成不可变快照；结果比较必须能够区分“相同输入不同配置”和“不同输入相同配置”。
6. 需求、测试点或用例发生修改时，系统应按追踪关系计算受影响范围。未受影响且指纹一致的下游结果可以复用，但必须记录复用依据；受影响结果必须转为待复核或失效。

#### 11.6.12 人工决策、版本发布与冲突处理

- 需求评审、测试点评审和用例评审必须提供审核人、审核角色、审核时间、审核意见、审核范围和审核版本。
- 人工审核可以逐条、批量、驳回、退回上游或直接确认无修改结果；批量确认必须保留明细ID，不能只保存一个数量。
- 同一产物被多人同时审核或修改时，必须使用版本号/乐观锁检测冲突；冲突不能静默覆盖，必须提示重新加载、比较和合并。
- Skill配置或Skill版本变更不得自动改变历史结果；新版本启用前必须通过输入输出契约、权限边界、代表性样例和回归测试。
- SkillChain蓝图和SkillChainConfiguration范围配置分别遵循11.6.17定义的生命周期及审计边界；启停、暂停、回滚和审计不得跨对象复用同一状态或操作语义。
- 需求分析、测试点和用例均必须支持差异对比，用户能够看到新增、删除、修改、证据变化和受影响下游节点。

#### 11.6.13 数据、成本和安全边界

- 执行前必须按当前Skill链、模型、MCP工具和知识库配置计算数据外发范围；涉及外部供应商时显示供应商、数据类型、费用状态和授权边界。
- 必须设置单次操作、项目和平台级调用次数、输入长度、运行时间和费用上限；达到上限时进入可解释的阻断或待确认状态。
- 需求原文中的提示注入、恶意指令或权限请求不能改变Skill选择、权限、项目范围或人工门禁；用户内容只能作为业务数据处理。
- 第三方Skill必须通过安装校验、版本锁定、权限声明和受控运行时；第三方Skill不能读取未授权项目数据，不能自行调用未声明工具。
- 运行日志只保留脱敏摘要、指纹、调用关联ID和结果状态；完整原文、密钥、令牌和敏感响应不得进入普通日志或审计列表。
- 费用失败、供应商超时、网络不可达、401/403、Schema不兼容和权限变更必须区分记录；重试前必须明确是否可能再次计费。

#### 11.6.14 深度验收矩阵

除正常主流程外，验收必须按“节点 × 配置层级 × 执行入口 × 结果状态”组合验证，至少包括：

1. 配置层级：全局继承、项目覆盖、功能覆盖、即时指定、配置冲突、配置撤销、Skill停用、版本回滚。
2. 节点链路：解析、需求分析、需求评审、需求拆解、测试点拆解、测试点评审、人工测试点评审、用例编写、用例评审、人工用例评审、最终用例集、执行和报告。
3. 执行入口：前端页面、REST API、Celery异步任务、智能体、MCP工具；所有入口必须生成一致的配置快照和状态语义。
4. 数据状态：正常、空输入、部分结果、重复提交、并发修改、上游变更、旧数据、字段错误、Schema错误、版本不兼容。
5. 权限状态：匿名401、项目外403、只读角色、项目管理员、平台管理员、第三方Skill未授权和工具权限不足。
6. 运行状态：成功、需要人工确认、被阻断、失败、超时、取消、重试、部分完成和回滚；任何状态都必须能定位到节点、配置、版本和原因。
7. 业务反向验证：修改需求分析必须能发现受影响测试点和用例；修改测试点必须能发现受影响用例；修改用例必须能使自动评审和自动化筛选失效；最终用例变更必须能阻止旧版本执行结果被误认为当前结果。

只有当以上链路的输入、输出、版本、权限、状态、人工决策和下游消费均有真实证据时，才允许将该需求标记为完成。


#### 11.6.15 执行链路进度、百分比与动态过程反馈

所有Skills及长时业务执行必须读取T169的同一条父级执行记录和节点执行记录。进度视图只是该运行记录的展示投影，不得另建一套前端任务状态或把某个业务结果JSON当作第二个权威状态源。

1. **进度记录。** 父级运行必须持久化运行ID、触发入口/操作人、工作流及版本快照、输入指纹、输出业务记录引用、状态、当前节点、事件修订序号、创建/启动/完成时间、取消/重试结果和安全错误码。每个节点记录节点ID/依赖、运行状态、Skill名称/ID/版本、输入/输出指纹、实际完成工作单元、当前轮次/分段、耗时、重试和下游消费引用。当前节点快照供恢复读取；节点历史和轮次证据必须能解释最终状态。
2. **进度口径。** 百分比属于本次用户操作的父级运行，仅按启动时已固定的工作计划及真实完成工作单元计算，不把以前完成的上游节点计入本次百分比。固定节点等权为默认；有可信、可重复验证的节点内工作量时才显示节点内百分比。无法量化节点内部工作时，百分比停留在最近完成边界，同时显示“第N项/共M项”和当前节点；不得用耗时计时器、前端动画、模型token估算或模型自述推进百分比。异步任务的队列等待时间与执行百分比分开显示。结果落库和最终一致性检查完成后，自动运行进度才可到100%。
3. **执行完成不等于质量通过或人工批准。** 页面必须分别显示运行状态、自动质量结论和人工审核状态。例如自动节点均完成但评审有问题时，可以显示“自动执行100% / 需修订”；评审通过但未人工审核时显示“自动执行100% / 等待人工审核”。禁止以100%、任务状态completed或Skill调用返回200替代“最终用例集已批准”。
4. **当前节点与动态文案。** 阶段文案通过链节点/实际执行子阶段的稳定键映射到平台维护的文字；只有后端确认进入该节点后才能显示“正在执行”。例如需求分析可显示“正在深度分析需求并检查分析测试点…”，用例编写可显示“正在检查已审核测试点的覆盖并补充遗漏用例…”。每轮模型调用、覆盖校验、去重、结果保存、自动评审都必须由真实运行回调推进；轮次完成不能提前代表后续校验、报告保存或整条链完成。模型不得直接提供系统状态文案。
5. **工作台弹窗与恢复。** 服务端持久化父级运行并返回运行ID后，打开可视化弹窗；此前仅显示“正在创建任务”，不显示虚构百分比。弹窗展示本次操作进度、当前节点/总节点、Skill与版本、阶段轨迹、已完成/运行中/排队/暂停申请/暂停确认/等待人工/重试/阻断/失败节点和结果入口。关闭按钮只隐藏弹窗，任务继续；暂停须在安全检查点得到Worker确认后才显示已暂停，非中断调用完成前显示“暂停中”；恢复必须从已持久化检查点继续并重新校验授权；取消是独立终态操作。刷新、路由跳转或重新登录后按运行ID恢复；同一页面只允许一个监控器，响应按运行ID和修订序号排序，旧响应不能覆盖新状态。初始提交的400/401/403/503必须作为提交失败展示，不能遗留幽灵运行或假成功。
6. **端到端链路与本次执行分区。** 点击生成用例后，服务端先按已发布链契约解析本次执行计划；弹窗展示从需求分析、需求评审、需求拆解、测试点拆解/评审、人工测试点确认到用例编写/评审及人工用例评审的完整来源链。每个节点必须标为“本次执行”“复用有效产物”“等待人工门禁”“不适用/未配置”“阻断”或“历史证据不足”，并展示来源运行、产物版本/指纹和审核状态。指纹、版本和审核证据均有效的上游产物只作为复用来源展示，不重复执行、不计入本次运行百分比；缺失或已失效节点仅在链配置允许且没有未满足人工门禁时执行；需要人工决策时暂停并提示决策者，不可自动放行。历史/旧记录无法证明Skill执行时不得显示为当前Skill成功。
7. **统一入口与订阅查询。** 需求分析页和用例页的按钮都调用同一个后端应用服务及工作流计划器；需求分析页先持久化本次测试点人工确认，再启动运行。服务返回父级运行ID后，两处打开同一运行视图。若保存审核成功但创建运行失败，准确显示“审核已保存、生成未启动”，用相同幂等请求可安全续试。运行快照由受权限保护的接口读取；短轮询/受控推送只传递该权威快照的更新，断线后按修订序号恢复。不得为进度另建无法与业务产物保持一致的旁路状态。
8. **验收要求。** 使用真实本地服务和MCP覆盖快速完成、长时间停留在模型节点、轮次边界、运行中刷新/关闭/重进、网络断开、队列发布失败与恢复、权限变更、取消停点、重复点击、超时、进程重启、部分结果、结果保存失败、上游版本变化、复用节点、待人工门禁和旧数据。核对Console、Network、运行ID/节点序号、持久化回读、结果/来源指纹及测试数据清理。

#### 11.6.16 “生成用例”单击操作与产物正确性契约

“生成用例”必须启动一个可恢复的端到端父级运行，而不是前端先后拼接互不相关的生成任务和评审任务。需求分析页的“确认审核并生成测试用例”和用例页的“生成/重新生成”必须调用同一个后端应用服务、解析同一个Skill链配置并返回同一格式的运行ID与状态；同一业务输入不得因同步/异步、Celery、REST、智能体或MCP入口不同而得到不同门禁或不同Skill语义。

执行顺序和数据边界如下：

1. **提交前门禁与冻结输入。** 只有需求分析质量状态允许生成、所有必需测试点审核已完成、用户选择的测试点均属于该审核版本、项目和操作权限有效、实际Skill/模型/提示词/工具策略可运行且预算/外发策略允许时，才创建父级运行。运行输入必须固定需求文档和解析证据指纹、需求分析记录ID/版本指纹、已审核测试点及其功能点/证据关系、审核人和审核时间、用户本次选择范围、项目、有效Skill链/配置/Skill/模型/提示词版本。Worker必须消费该冻结输入，禁止在排队后再查询“最新分析”替换本次输入。
2. **重复提交与并发保护。** 每次点击带有幂等键；浏览器超时后重试同一请求须返回原运行，而不是新建记录、重复扣费或重复写入。用户明确执行“重新生成”才建立新运行和新产物版本。相同来源版本及选择范围的活跃运行不得竞争写入；若输入在运行期间被修改，运行结果仍绑定原指纹并被标为旧版本/待复核，不能成为当前结果。
3. **真实用例编写Skill节点。** 用例生成Skill必须实际处理冻结的结构化需求、已审核测试点和证据，并产生通过Schema校验的用例内容与逐条来源关系。Skill输出必须由CaseGeneration业务服务校验、去重、执行范围约束并持久化；“planned”、回显、提示词计划或生成后旁路调用都不算真实执行，不能进入用例记录或显示为成功。五轮/多分段模型工作须如实显示实际轮次和分段；模型失败、确定性基线或回退必须显示为独立来源/状态，遵从项目配置的失败策略，不能覆盖成Skill成功。
4. **覆盖与业务校验节点。** 模型生成之后的结构化解析、测试点范围校验、功能点/证据追踪、去重、覆盖率及覆盖缺口计算、结果持久化都属于实际工作流节点或可审计子阶段。五轮结束不等于生成节点完成；达到100%前必须完成这些校验并将生成记录与父级运行、源分析版本、测试点审核版本及Skill执行ID原子关联。
5. **真实用例评审Skill节点。** 自动评审必须在生成记录保存成功后运行，并消费该父级运行生成的确切用例版本；不得评审另一个最新记录或人工修改后的版本。确定性字段/重复检查、模型评审各轮、报告Schema校验和报告持久化须分别有执行状态。评审结果有问题但评审执行完整时，运行显示“需修订/评审未通过”，而非模型调用失败；评审执行失败时保留已生成草稿，父级运行显示部分完成，提供仅重试评审节点的恢复入口。
6. **人工评审与最终资产。** 用例评审Skill的结果不能代替人工审核。自动链完成后，工作流状态仍可为“等待人工评审”；只有人工确认/修订并完成要求的重新评审，才能标记为最终用例集。人工修改必须生成新版本，使针对旧版本的自动评审、自动化筛选和执行结果失效。
7. **统一业务入口。** 需求分析页先保存并确认人工测试点审核；不完整审核不得启动父级运行。保存审核与创建运行之间失败时，页面须准确表示“审核已保存、生成未启动”，可以安全续试。用例页和需求页随后进入同一个可恢复进度界面。单独的“重新评审”操作是以某个明确用例版本为输入的新运行，必须链接回原生成运行，不能改写其历史。
8. **旧记录兼容。** 历史CaseGenerationRecord可能只有需求文档ID、测试点ID、JSON报告和旧task_runtime，没有分析版本、Skill节点或父级运行。读取旧记录时保留既有数据并标为“历史/链路证据不完整”；不得自动补造节点成功、Skill版本或输入指纹。新运行和旧接口需有显式兼容映射，过渡期间同一执行不能同时由旧任务状态和新运行状态竞争更新。
9. **自动化下游门禁。** 只有当前源指纹一致、生成输出校验通过、自动评审结论满足配置要求且人工审核状态满足产品策略时，才能进入自动化筛选、UI/API/性能执行和最终报告。任何失败、部分输出、旧版本、待审核和越权输入都必须阻断或明确降级为不可发布草稿。

#### 11.6.17 蓝图、范围配置与单次运行的生命周期边界

平台必须分别管理三个对象，页面按钮、权限、状态和审计记录不得混用：

1. **SkillChain蓝图。** 编辑产生草稿版本；验证通过后发布为不可变版本。启用/暂停针对指定蓝图版本：启用允许新运行选择该版本，暂停阻止新运行进入，但不影响已启动运行。回滚必须明确选择一个历史已发布版本，并以其内容复制创建新版本，再经过验证和启用；当当前版本没有更早的可回滚目标（如首次创建）时，回滚按钮禁用并显示“暂无可回滚版本”，API返回可识别的`no_rollback_target`冲突，不创建伪造历史或空操作事件。
2. **SkillChainConfiguration范围配置。** 全局/项目/功能/即时配置仅负责选择蓝图版本、覆盖字段及生效范围。首次创建的配置写入初始基线版本和创建审计；没有更早配置版本时，配置回滚禁用并显示“暂无可回滚配置版本”。配置启用/停用只控制该范围解析，不等同于启动/暂停蓝图；配置回滚只恢复配置记录的历史值，不等同于蓝图版本回滚。配置解析/预览是只读操作，不启动执行。
3. **单次运行。** 用户明确执行“运行蓝图/生成用例”才创建运行ID并开始一次运行；运行详情提供开始、请求暂停、从检查点恢复和取消。暂停必须等待安全检查点确认，恢复后仍使用原运行配置/输入快照并重新核验当前用户权限；蓝图或范围配置之后发生变化，不得改写已运行快照。暂停蓝图不自动暂停已有运行，暂停单次运行也不改变蓝图或范围配置的启用状态。
4. **审计。** 蓝图审计覆盖创建、修改、验证、发布、启用、暂停、回滚、归档；配置审计覆盖首次创建、修改、启停、撤销、配置回滚；运行审计覆盖开始、暂停请求/确认、恢复、取消、重试和终态。创建必须产生第一条基线事件。服务端从认证会话写入操作者用户ID、显示名、角色/授权范围、时间、对象/项目范围、前后版本、差异摘要、理由、结果和关联运行ID，不接受客户端伪造的操作者字段。若策略要求双人复核，复核人、角色、时间、决定和意见与操作者分字段保存。审计历史仅对具有同范围审计读取权限的用户开放；平台审计权限可读全局，项目审计权限限本项目，其他用户返回403。敏感提示词、密钥及业务原文须脱敏。历史旧记录缺失身份证据时显示“历史记录/操作者未知”，不得补造。

验收必须在真实工作台分别验证蓝图页、范围配置页和运行详情页的动作与状态；确认蓝图暂停不会误停既有运行、运行暂停不会停用蓝图、两种回滚对象不会混淆，审计历史可按对象/版本查询且权限隔离正确。

## 12. F8 智能检索系统

### 12.1 检索方式

| 检索方式   | 说明            | 适用场景   |
| ---------- | --------------- | ---------- |
| 语义检索   | 向量相似度      | 模糊查询   |
| 关键词检索 | PostgreSQL FTS 排名 | 精确查询；P1再评估真正 BM25 |
| 混合检索   | pgvector + PostgreSQL FTS | 默认方式 |
| 元数据过滤 | 按项目/类型筛选 | 精确筛选   |
| 个性化检索 | 结合用户偏好    | 个人化结果 |
| 上下文感知 | 结合对话上下文  | 连续对话   |

### 12.2 检索配置

| 配置项     | 默认值  |
| ---------- | ------- |
| Top-K      | 5       |
| 相似度阈值 | 0.65    |
| 分块大小   | 500字符 |
| 重叠长度   | 50字符  |

P0 使用 PostgreSQL 全文检索（`tsvector`/`tsquery`/数据库排序）作为关键词召回，不把 FTS 排名无条件宣称为 BM25。真正 BM25 只有在单独验证数据库扩展、运维成本和排序收益后，才作为 P1 方案引入。

### 12.3 RAG 二阶段产品规划

#### 12.3.1 阶段定位与产品判断

当前知识库已经具备文档解析、分块、审核和基础检索能力，但还不能稳定支撑“基于企业知识回答并给出依据”的产品承诺。RAG 二阶段的目标不是增加一个框架名词，而是把知识库升级为可控、可解释、可评估的知识增强能力。

本阶段优先解决三个真实问题：

1. 用户问到接口名、错误码、字段名或版本号时，关键词检索不能丢失精确匹配；
2. 用户用自然语言描述问题时，语义检索能够找到同义或相近内容；
3. 智能体回答或生成测试用例时，用户能够看到引用来源，并确认答案没有跨项目或跨审核状态取数。

本阶段不做以下事情：

- 不把 LlamaIndex 作为业务数据库或权限系统；
- 不新增独立向量数据库，继续以 PostgreSQL + pgvector 为数据底座；
- 不把历史 JSON 向量直接当作生产检索结果，旧数据必须经过明确的重建或标记；
- 不承诺“有知识库就一定正确”，没有足够证据时必须回答“未找到可靠依据”；
- 不在本阶段同时引入 MCP、多智能体框架或新的主编排器。

#### 12.3.2 目标用户与核心场景

| 用户 | 场景 | 用户应看到的结果 |
| --- | --- | --- |
| 测试工程师 | 搜索某个错误码、接口字段或历史缺陷 | 结果按相关性排序，显示来源、项目、版本和审核状态 |
| 测试负责人 | 让智能体参考项目规范生成测试点或用例 | 生成内容带引用；引用不足时明确提示需要人工确认 |
| 开发工程师 | 查询接口契约、环境约束和已知问题 | 精确命中关键词，同时补充语义相近内容 |
| 管理员 | 选择知识模型、查看索引状态、处理失败重建 | 能看到模型、索引版本、失败原因、耗时和成本摘要 |

P0 首个闭环为：创建/上传知识 → 解析 → 人工审核 → 建立索引 → 混合检索 → 展示引用 → 智能体消费引用。

P1 才考虑个人化排序、自动知识沉淀、复杂查询改写和更多在线连接器；这些能力不能阻塞 P0。

#### 12.3.3 知识生命周期

```text
导入/上传
   ↓
解析与分块
   ↓
人工审核
   ↓
Embedding 生成
   ↓
pgvector + 关键词索引
   ↓
索引可用
   ↓
混合检索与引用
   ↓
文档变更/撤销 → 旧索引失效 → 增量或全量重建
```

只有同时满足以下条件的内容才能参与默认检索：知识库启用、文档解析成功、审核通过、索引状态可用、项目和用户权限匹配。审核撤回、文档删除、项目成员变更后，结果必须立即或在明确的索引刷新窗口内失效。

同一索引版本只能使用一种 Embedding 模型和固定维度。更换模型或维度时必须生成新的索引版本和对应存储，不能混查不同维度向量；新版本评测通过后才可原子切换为当前版本，旧版本保留至确认可回滚后再清理。历史 HashVectorizer 向量不得直接作为生产 RAG 结果。

#### 12.3.4 检索产品要求

1. 检索模式至少支持语义、关键词、混合三种模式，默认混合；用户能够看见当前模式。
2. 过滤条件至少包括项目、知识库、知识类别、来源类型、文档版本和审核状态；权限过滤由后端完成，前端参数不能绕过。
3. 混合检索必须先分别取候选，再去重和融合排序；不能简单把两个分数直接相加而不做归一化。
4. 对错误码、接口名、字段名、版本号等精确文本，关键词结果必须有机会进入最终 Top-K。
5. 每条结果返回标题、来源类型、文档位置或分块序号、项目、版本、审核状态、检索模式、分数和稳定引用 ID。
6. 没有可靠结果时返回空结果和下一步建议，不生成无来源的确定性答案。
7. 结果上下文必须有长度上限、重复片段去重和最大引用数量，避免把整篇文档发送给模型。
8. 可选重排序只能使用明确配置且能力匹配的模型；重排序失败时保留混合检索结果并标记失败原因。
9. 建立索引前必须执行敏感信息检测；包含 API Key、密码、Token、个人信息或明确禁止外发内容时，默认阻止外部 Embedding，或仅在完成脱敏并取得相应授权后发送。
10. 全量重建前必须显示预计文档数、分块数、模型调用量和费用区间；超过管理员设定的预算或并发上限时必须等待确认或自动停止。

#### 12.3.5 智能体增强要求

- 智能体只有在意图需要知识依据时才触发检索，不对简单 CRUD 或纯计算请求强行检索。
- `retrieve_node` 接收用户输入、项目上下文、知识库范围和权限上下文，返回统一的 `knowledge_context` 与引用列表。
- 生成答案时必须区分“检索到的事实”“模型推断”和“待用户确认”，不能把推断写成文档原文；每个关键结论必须能映射到一个或多个引用。
- 没有足够证据时，智能体必须返回“证据不足/未找到可靠依据”状态并请求澄清，不得为了保持对话流畅而补写看似合理的事实。
- 当检索服务不可用、模型未配置或引用不足时，智能体应说明限制并请求用户补充，而不是静默使用跨项目或未审核内容。
- RAG 结果不改变任务权限；检索到的文档不能自动获得执行工具、访问环境或外发数据的权限。

#### 12.3.6 用户界面与反馈要求

知识库工作台必须覆盖：

- 索引状态：未建立、排队中、处理中、可用、部分失败、失效；
- 空数据：没有知识库、没有审核通过内容、没有可用索引时分别说明原因；
- 成功：展示检索结果、引用和检索模式；
- 字段错误：明确指出项目、模型、Top-K、阈值或过滤条件的问题；
- 401/403：区分未登录和无权访问，不泄露资源是否存在的敏感信息；
- 服务失败：显示是解析、Embedding、索引、检索或重排序失败，并提供可安全重试的入口；
- 变更提示：修改文档或审核状态后提示索引可能需要重建。
- 全量索引：展示预计成本和影响范围，管理员确认后才执行；执行中可查看进度、取消任务，失败时保留上一版可用索引。
- 版本管理：管理员可查看当前/上一版索引，并在新版本失败或质量不达标时回滚到上一版；回滚后重新执行权限校验。
- 数据外发：使用外部 Embedding 前展示供应商、地域、发送内容类别和脱敏结果；未获授权时只能使用本地或阻止索引。

#### 12.3.7 RAG 二阶段验收指标

以下指标针对二阶段验收集，不替代全平台指标：

| 指标 | P0 目标 | 说明 |
| --- | --- | --- |
| 权限隔离 | 未授权召回 0 条 | 覆盖跨项目、归档知识库、未审核文档和撤销成员 |
| 引用完整率 | ≥98% | 有内容的最终回答必须能回溯到稳定引用 |
| 关键词命中率 | ≥95% | 错误码、接口名、字段名、版本号测试集 |
| 混合检索 Recall@5 | ≥90% | 人工标注的项目知识测试集 |
| 无依据拒答准确率 | ≥90% | 无相关知识时不编造来源 |
| 索引幂等性 | 100% | 同一文档重复索引不产生重复有效分块 |
| 索引失败可恢复率 | 100% | 失败可重试，不破坏上一版可用索引 |
| 交互响应 | 普通检索 P95 ≤2秒 | 不含外部模型冷启动和大规模重建 |
| 生产降级 | 可回到原生检索 | LlamaIndex 不可用时不影响已审核知识检索 |
| 版本切换 | 原子切换、可回滚 | 新索引失败不影响上一版服务 |
| 外部数据治理 | 未授权敏感内容外发 0 次 | 覆盖索引前检测、阻止、脱敏和审计 |
| 成本控制 | 超预算任务不自动执行 | 全量重建需预估、确认、限流和可取消 |

验收必须同时包含离线标注集、后端专项测试、全量回归、真实本地 API、工作台操作和跨项目权限验证；不能只用“接口返回 200”作为 RAG 质量证明。

#### 12.3.8 服务器端模型调用与部署网络门禁

连接测试、Embedding、需求分析、用例生成和智能体调用均由后端服务进程发起外部模型请求，浏览器能够访问互联网不能替代服务器端出网能力。目标部署环境必须在上线前明确以下条件：

- Django、Celery Worker 和需要实际调用模型的服务身份，均可解析供应商域名并建立 TCP 443/TLS 连接；
- 公司网络要求代理时，代理地址、认证方式、CA 证书和适用进程必须完成配置，后端与 Worker 不能只依赖开发者终端的代理；
- 供应商域名、地域地址、端口和网络出口策略纳入部署清单；禁止通过关闭整体安全策略来解决单个服务的出网问题；
- 连接测试必须在与线上相同的后端运行身份和网络路径下执行一次真实短调用；只用浏览器、管理员电脑或目录 HTTP 200 不能作为通过依据；
- 出网失败时，页面需区分 DNS、TCP/TLS、代理、供应商 HTTP、鉴权、额度和模型能力问题，并给出管理员可执行的处理建议；不得把所有失败都显示为“测试未通过”；
- 模型基础地址必须执行供应商域名/端口白名单、解析 IP 校验和私网地址拦截；禁止访问回环、RFC1918、链路本地、云元数据等地址，并防止 DNS rebinding；管理员权限不能替代目标地址安全校验；
- 自动化测试默认使用 Mock Provider；只有管理员或用户明确确认的连接测试、目标部署验收允许一次不携带业务数据的短调用，不自动重试，不以此替代单元和集成测试；
- 模型 Key、代理认证信息和完整上游地址中的敏感部分不得写入日志、审计详情或前端响应。

服务器端出网未通过时，模型连接测试及依赖真实模型的功能只能标记为“环境未就绪”，不能标记为产品能力已验收。

连接测试的错误分类、目标地址安全校验和前端可理解反馈由独立任务 T146 实现；T145 只负责目标部署环境的出网与代理验收。

### 12.3.9 模型连接配置审批与跨地域使用治理（二期）

第三方代理、自建境外 Gateway、境外服务器直连和跨地域模型执行不能仅作为模型配置中的一个 URL。它们会影响数据去向、密钥暴露范围、费用、供应商责任和项目权限，必须纳入独立的连接配置审批生命周期。

#### 连接配置状态

连接配置至少包含以下状态：

```text
草稿 → 待审核 → 审核通过 → 已验证 → 已启用
                  ├→ 已拒绝
                  ├→ 已暂停
                  └→ 已撤销
```

- 新建的第三方代理、自建 Gateway 或境外连接默认为“待审核”，不得直接用于生产调用；
- “审核通过”只表示治理和权限审批通过，不代表网络或模型调用成功；
- “已验证”必须由与线上相同身份的 Django/Celery Worker 完成安全连接测试；
- 只有同时满足“审核通过、已验证、已启用、当前用户和项目有权限”时，连接才可以用于业务调用；
- 连接过期、被撤销或被暂停后，所有引用它的模型必须停止调用或切换到明确批准的备用连接；
- 超时默认拒绝，不得自动放行。

#### 审核信息

审核申请必须记录：

- 连接类型：官方直连、第三方代理、自建 Gateway 或境外部署；
- 端点地址、部署地域、协议类型和支持供应商；
- 模型范围、能力范围和模型 ID 映射；
- Prompt、文件、测试数据和模型结果的数据去向；
- 第三方是否保存数据、密钥归属、预计费用和额度；
- 允许使用的租户、项目、环境和角色范围；
- 连接测试结果、失败阶段、测试时间和执行身份；
- 申请人、审核人、审核意见、有效期、撤销原因和变更记录。

#### 审批规则

- 普通用户不能创建、修改或启用任意代理和境外连接；
- 平台管理员负责连接创建、域名/IP 白名单和凭据管理；
- 涉及生产数据、敏感数据、跨境传输或预计费用超过阈值时，必须触发 Human-in-the-Loop 审批；
- 高风险连接原则上需要双人确认；
- 审批人不能审批自己创建且涉及自身项目的高风险连接；
- 审批通过后修改端点、协议、地域、凭据归属、数据范围或费用策略，必须重新审核；
- 连接健康失败不应自动改变审批状态，但必须阻止调用并通知管理员；
- 所有创建、提交、批准、拒绝、启用、停用、暂停、撤销、切换和密钥轮换操作必须写入审计链。

#### 业务调用前检查

模型调用前必须校验连接状态、项目/租户范围、用户权限、模型能力、数据策略和当前健康状态。备用连接只能在管理员或功能策略明确允许时使用，并在页面显示实际生效的连接和切换原因。

本节是二期连接架构的产品约束；在对应需求审核通过并拆入 `TASKS_V5.0.md` 前，不新增生产连接字段，不开放第三方代理或境外连接的业务入口。

### 13.4 模型使用路由与功能选择整改计划（已审核，按任务执行）

当前模型配置仅覆盖模型注册、按类型默认和基础路由，尚未完整满足“平台全局使用或各功能独立选择模型”的产品要求。本节作为新增整改计划，审核通过前不计入已完成需求，也不改变现有任务完成统计；整改只新增或修正本节范围内的能力，不追溯性否定之前已完成并验收的功能，历史差异通过独立任务兼容处理。

#### 13.4.1 模型选择层级

所有实际调用大模型的功能必须提供模型选择入口，选择优先级统一为：

1. 当前功能本次操作临时选择的模型；
2. 当前功能已保存的模型绑定；
3. 平台全局默认模型；
4. 管理员明确启用的备用模型；
5. 用户主动选择的确定性基线。

纯 CRUD、文件上传、确定性计算等不调用大模型的功能不增加无意义的模型选择控件。

全局默认模型用于所有未单独配置的兼容功能，但不能强行用于不支持目标能力的任务。文本、视觉、向量、语音和媒体任务必须按模型能力过滤；没有兼容模型时应明确阻止执行并提示配置，不得静默调用错误模型。

#### 13.4.2 功能级模型入口

以下功能必须有独立的模型入口，并显示“继承全局默认”选项：

| 功能 | 选择范围 | 说明 |
| --- | --- | --- |
| 需求深度分析 | 全局默认 / 功能绑定 / 本次选择 | 需求拆解、功能模块、功能点和测试点 |
| 截图与视觉分析 | 全局默认 / 功能绑定 / 本次选择 | 仅展示视觉或全模态模型 |
| 测试用例生成 | 全局默认 / 功能绑定 / 本次选择 | 五轮递进生成 |
| 测试用例评审 | 全局默认 / 功能绑定 / 本次选择 | 五轮评审与覆盖检查 |
| 智能体执行 | 全局默认 / 智能体绑定 / 本次选择 | 智能体已有显式模型时优先使用 |
| 报告生成 | 全局默认 / 功能绑定 / 本次选择 | 生成报告和覆盖度说明 |
| 知识库模型任务 | 全局默认 / 功能绑定 | 向量化、重排序等按能力过滤 |

管理员可以在模型配置页设置全局默认模型和功能绑定；功能页面允许用户在本次操作中临时切换，并必须展示最终生效的供应商、模型、能力类型和选择来源。

#### 13.4.3 失败与备用策略

- 未配置模型：阻止模型操作，提示配置入口和所需能力。
- 模型能力不匹配：阻止调用，提示选择兼容模型。
- Key、权限、地域、额度、网络或供应商失败：显示具体阶段和模型信息，支持重试或切换。
- 备用模型：仅在管理员或功能策略明确允许时启用；切换必须在页面提示并写入审计。
- 确定性基线：只能由用户主动选择，不能用“模型评审降级”或“没有可用模型”模糊替代。

#### 13.4.4 五轮用例生成语义

五轮表示同一份需求的递进分析和覆盖补全，不是重复生成五份独立用例：

1. 主流程、验收标准和核心功能点；
2. 异常、权限、输入校验、依赖失败和安全风险；
3. 边界、状态、并发、重复提交、恢复和数据一致性；
4. 模块关系、数据流、接口契约和跨模块业务链路；
5. 测试点、风险和回归影响的最终遗漏检查。

每轮必须输入需求正文、深度分析结果、功能模块、功能点、测试点、联合场景和已有用例，只返回新增场景。结果必须保存本轮分析重点、本轮新增数、累计数、实际模型、切换状态和失败原因。

#### 13.4.5 可理解性与审计要求

页面禁止直接展示 `initial`、`requirement_compare` 等内部阶段码。每轮应显示中文阶段名称、本轮新增数量和累计数量。历史记录缺失累计值时由服务端兼容计算。所有模型调用必须记录模型配置、供应商、模型名称、选择来源、是否备用切换和失败原因，但不得记录 API Key 或原始敏感凭据。

本节对应的实施任务见 `TASKS_V5.0.md` 中“模型使用路由与功能选择整改计划（已审核，按任务执行）”。

### 21.5 平台账号开通与同事授权闭环【P0 补漏】

管理员必须能够完成“开通同事账号→分配平台角色→加入项目→同事登录并使用”的完整流程，不能要求多人共用管理员账号，也不能只提供零散的后端接口。

#### 账号开通方式

- 管理员可以创建邀请或生成一次性开通链接；
- 被邀请人使用自己的账号标识和密码完成激活；
- 邀请链接必须具备有效期、一次性使用、撤销和审计能力；
- 如果系统支持管理员创建临时密码，首次登录必须强制修改，管理员不能查看或再次读取密码；
- 保留公开注册能力时，新注册用户默认进入待授权/访客状态，不能自动获得项目或平台管理权限；
- 管理员可以重新发送邀请、撤销未使用邀请、停用账号和发起密码重置；
- 不允许通过前端、日志或接口返回明文密码、邀请密钥或重置令牌。

#### 授权流程

平台角色和项目角色必须在产品上明确区分：

```text
账号开通
  → 平台角色（管理员/测试负责人/测试工程师/开发工程师/访客）
  → 项目成员关系（owner/manager/member/viewer）
  → 项目功能权限
  → 登录后可操作范围
```

- 管理员可以从用户列表进入授权流程；
- 管理员可以看到用户当前平台角色、账号状态、所属项目和项目角色；
- 管理员可以将已注册用户加入一个或多个项目，并设置项目角色；
- 需求导入、解析和深度分析至少要求项目 owner、manager 或平台管理员权限；
- 平台管理员权限不能绕过后端项目边界、目标地址安全校验或数据合规策略；
- 角色、项目成员、账号启停、邀请、重置和撤销均必须写入审计记录；
- 页面必须说明“平台角色变更”和“项目角色变更”不是同一项操作，避免管理员误以为只改一次角色即可授权全部功能。

#### 账号状态

账号至少支持：待邀请、待激活、已启用、已停用、已锁定、已撤销。停用、撤销或项目移除后，已签发的访问令牌必须按安全策略失效或在短时间内失效，不能继续访问原项目数据。

### 21.6 用户访问地址与部署入口【P0 补漏】

平台必须告诉管理员“应该把哪个地址给同事访问”，不能要求管理员在公网 IP、后端端口、Docker 容器 IP、数据库端口和 SSH 地址之间自行猜测。

#### 访问地址配置原则

- 生产环境必须显式配置一个规范的用户访问地址 `PUBLIC_APP_URL`，优先使用 HTTPS 域名；
- 没有域名时，可以使用公网 IP 加映射端口，例如 `http://公网IP:8090`，但必须明确这是临时或受限部署方式；
- API 地址默认使用同源路径；只有前后端分离部署时才额外配置 `PUBLIC_API_URL`；
- 内网地址、容器地址、数据库地址、Redis 地址和 SSH 地址不得作为普通用户访问地址展示；
- 系统不得自动枚举并向用户暴露服务器所有网卡 IP；
- 管理员可查看当前规范访问地址、协议、端口、访问范围（公网/内网）、TLS 状态和最近检查时间；
- 管理员可复制用户访问地址和邀请链接；
- 访问地址变更后，旧地址的处理方式、影响范围和生效时间必须可见。

#### 地址分类

| 地址类型 | 使用者 | 是否可分享 |
|---|---|---|
| 用户访问地址 | 同事、项目成员 | 可以 |
| 管理员入口地址 | 管理员 | 按部署策略 |
| API 内部地址 | Backend、前端代理 | 不直接分享 |
| Docker/数据库/Redis 地址 | 容器内部 | 不可分享 |
| SSH 管理地址 | 运维管理员 | 不可作为产品入口 |

#### 验收要求

- 管理员从工作台可以看到规范用户访问地址；
- 同事使用该地址可以完成邀请激活、登录和进入已授权项目；
- 访问地址错误、端口未开放、反向代理错误和 API 不可达时，页面给出可操作提示；
- 访问地址页面不得显示密钥、密码、内部服务地址或未经配置的推断 IP；
- 服务器部署验收必须记录实际用户入口，不得用 `127.0.0.1`、Docker 内网 IP 或仅后端 `8000` 端口替代公网入口。

### 21.7 长输入与长结构化结果分段生成闭环【P0 补漏】

需求分析只是长文本调用的一个入口。用例生成、五轮评审、报告生成和智能体结构化节点同样不能依赖一次无限增长的模型请求；固定提高 `max_tokens` 不能作为长内容成功的最终方案。

#### 统一运行规则

- 调用前必须根据供应商、模型上下文窗口、输入长度、结构化 Schema 和费用/超时策略计算预算；输入或预计输出超过单次预算时，自动生成可追踪的分段计划；
- 分段必须优先按文档章节、需求条目、用例集合、评审轮次或证据边界切分，不得简单按字符截断导致语义和引用丢失；每段必须携带项目、文档、需求/用例和证据 ID；
- 每次模型调用必须返回段编号、Schema 版本、续接游标、是否最终段和实际结束原因；`finish_reason=length` 只能进入受控续接/重分段流程，不能被当作成功 JSON；
- 合并必须是确定性的：按稳定 ID 去重、校验引用和必填字段、保留来源段和调用轨迹；重复提交或重试不得产生重复需求、用例、评审结论或报告内容；
- 某一段失败时，系统必须保留已完成段、显示部分结果状态和失败段，可单段重试或从游标继续；不得静默切换供应商、无限自动重试或把部分结果标记为完整/模型已验证；
- 页面和 REST 必须区分处理中、部分完成、已完成、可恢复失败和不可恢复失败，并给出当前段、失败原因、重试边界和费用提示；
- 该规则统一适用于需求分析、用例生成、五轮评审、报告生成、智能体结构化输出及后续新增的长结构化模型调用。

### 21.8 需求分析结果可重复性与覆盖完整性【P0 补漏，T155B】

需求深度分析属于模型辅助的结构化抽取，不能仅以“返回了合法 JSON”判定结果完整。相同需求、相同解析证据、相同模型路由和相同 Prompt 基线的重复分析必须具备可比较的指纹、证据覆盖状态和差异报告。

- 每次分析必须记录源文档指纹、解析证据指纹、实际模型路由、Prompt 配置版本/标识、Schema 版本、分段执行轨迹和完整性状态。
- 分析结果必须区分 `complete`、`partial`、`needs_review` 和 `failed`；分段失败、输出截断、证据未覆盖或结果数量显著下降时，不得展示为完整模型验证。
- 每个模块、功能点、联合场景和测试点应尽量关联来源证据；系统必须统计已覆盖、未覆盖和未提供引用的证据，不能用结构合法替代覆盖证明。
- 清除当前分析记录时，需求正文、解析证据和最近一次可比较分析基线必须按安全摘要保留，用于下一次分析的稳定性对比；历史用例生成记录不受影响。
- 重复分析的数量变化必须生成差异摘要。新结果低于上一版时，不得静默宣称两版等价，必须提示人工复核并保留当前结果状态。
- 只有完整性状态为 `complete` 的结果才可作为“已验证需求分析”进入后续用例生成；`partial` 和 `needs_review` 必须在工作台明确提示。
- `8192` 等单次输出上限只属于单段预算，超过预算必须通过可追踪分段、续接或重规划处理；合法但不完整的 JSON 不得被视为完整结果。

#### 验收要求

- 输入和输出均超过一次调用预算时，能够通过多个受控调用完成，并产生一份去重、字段完整、证据可追溯的最终结果；
- 任一中间段发生超时、服务失败、401/403、无效 JSON 或输出截断时，已完成内容不丢失，单段重试不会重复副作用；
- 空输入、字段错误、旧数据/旧接口、权限边界、供应商不支持、上下文边界和取消/恢复均有明确业务状态；
- 日志、调用轨迹和前端反馈不得泄露 Key、密码、完整敏感原文或代理凭据；未完成的部分结果不得进入“已验证”统计。

### 21.9 需求分析五轮递进复核与覆盖补全【P0 补充，V5.4 已评审，T155C】

本节将“需求分析”与“长文本分段”明确区分。分段是单轮模型调用的技术预算措施；五轮是针对同一份需求的五次递进式语义复核。一次成功的需求分析必须完成 5 个语义轮次，但每个轮次可以根据输入和输出预算拆成多个受控分段，因此 `round_count` 不得用 `segment_count` 代替。

#### 21.9.1 五轮递进规则

| 轮次 | 目标 | 重点检查 |
| ---- | ---- | -------- |
| 第 1 轮 | 建立基线 | 模块、功能点、流程、数据对象、初始测试点和原文证据 |
| 第 2 轮 | 补异常风险 | 异常、权限、输入校验、依赖失败、网络失败、安全和错误提示 |
| 第 3 轮 | 补边界状态 | 边界值、空值、重复操作、并发、状态切换、恢复、重试和数据一致性 |
| 第 4 轮 | 补关系联动 | 模块依赖、数据流、接口契约、跨模块流程、状态联动和联合测试点 |
| 第 5 轮 | 最终复核 | 未覆盖证据、遗漏项、重复项、冲突项、测试类型和高风险回归范围 |

第 2～5 轮必须重新读取完整需求正文和全部解析证据，同时携带前轮累计结果、已覆盖证据、未覆盖证据及前轮问题清单。后续轮次不得只看上一轮新增内容，也不得覆盖掉已有的有效分析项。

#### 21.9.2 增量结果和最终结果

- 每轮只允许产生有证据依据的新增项、修正项、重复项、冲突项和未覆盖证据说明；不得通过重复生成相同测试点虚增覆盖率。
- 系统必须按稳定业务特征去重，保留首次来源轮次、补充轮次、证据 ID 和变更原因；冲突不能静默覆盖，必须进入人工复核清单。
- 只有 5 轮全部完成、最终结构映射完整、测试点字段完整、证据覆盖状态明确且没有未处理冲突时，结果才允许进入人工审核表；人工审核表支持“全部勾选”“标记所选为已审核”和已审核集合展示，用例生成只能读取该集合。
- 5 轮完成不等于自动通过。人工仍需审核最终测试点的模块、功能点、描述、测试类型和原文依据；审核通过后才允许生成用例。

#### 21.9.3 进度、失败和费用边界

- 前端必须分别显示“分析轮次：第 N/5 轮”和“本轮分段：第 M/K 段”，禁止将“分段 5/5”误标为“五轮分析完成”。
- 每轮必须记录分析重点、实际模型、调用来源、分段轨迹、本轮新增数、修正数、重复数、累计数、覆盖率、耗时和失败原因。
- 任一轮失败、超时、无效 JSON、输出截断或证据校验失败时，整体结果只能为 `partial` 或 `failed`，已完成轮次和失败轮次必须可恢复，不能进入完整审核或用例生成。
- 自动重试、分段拆分和单轮恢复必须有次数、最大分段数、超时和费用边界；不得无限重试或静默切换未授权模型。页面应展示本次实际调用次数和可预估的最大调用范围。

#### 21.9.4 覆盖率口径

覆盖率至少分为原文证据覆盖率、功能点覆盖率、测试维度覆盖率和联动覆盖率。模型无法从原文确认的内容必须标记为待人工确认或未覆盖，不能为了达到 100% 自动补写需求事实。产品目标是通过五轮递进复核显著提高召回率和覆盖率，而不是承诺模型结果必然达到 100%。

### 24.1 RAG 二阶段专项验收补充

RAG 二阶段必须满足以下条件后，才可将“知识库模型任务”和“智能体知识增强”标记为完成：

1. 真实 PostgreSQL + pgvector 环境完成迁移、索引和回填验证；本地 SQLite 仅作为明确的降级测试环境。
2. 至少建立一套包含接口名、错误码、字段名、版本号、自然语言问题、跨项目干扰项和无答案问题的人工标注集。
3. 同一查询分别验证关键词、语义和混合检索结果，能够解释最终排序和引用来源。
4. 对未登录、跨项目、未审核、已归档和成员撤销场景完成 401/403/空结果/零泄漏验证。
5. 文档重新上传、重复索引、审核撤回、索引失败、重试和旧版本保留均有可重复测试。
6. LlamaIndex 适配关闭或异常时，原生 Django/pgvector 检索仍能安全返回；不能出现无提示的空上下文。
7. 智能体输出至少包含引用、证据不足提示和失败原因，不得把模型推断伪装成知识库原文；关键结论没有引用时不得标记为有依据。
8. 更换 Embedding 模型或维度时，新旧索引可并存、可评测、可原子切换和可回滚，不发生不同维度混查。
9. 向外部 Embedding 发送内容前完成敏感信息检测、脱敏/阻止、授权提示和审计；全量重建在预算确认前不能启动。
10. 目标部署环境必须由 Django 和 Celery Worker 的实际运行身份完成 DNS、TCP/TLS、代理继承和一次真实短调用验证；网络未就绪时不得标记模型能力验收通过。
11. 模型连接地址必须通过目标安全校验；连接测试页面必须展示 DNS、TCP/TLS、代理、供应商 HTTP、鉴权、额度和模型能力的脱敏失败阶段，并提供对应处理建议。
