## 任务执行规则

```yaml
执行规则:
  1. 每个任务执行前输出确认信息，等待用户回复
  2. 每个任务完成后必须经过两轮测试验证
  3. 复杂功能必须先输出开发计划，等待用户确认
  4. 每个任务完成后立即停止，等待用户确认
  5. 禁止跨任务编码、禁止推测用户意图
  6. 自动化测试默认使用Mock；仅管理员或用户明确授权的连接测试、目标部署验收允许一次不携带业务数据的短调用，禁止自动重试和无授权计费调用
  7. 所有LLM调用必须包含重试和降级机制
  8. 基于正常社会思维和人类使用逻辑进行开发
  9. 任务ID保持稳定；当新增任务形成前置依赖时，依赖关系优先于编号顺序
  10. 🟦 每个业务模块必须按“后端能力→对应前端→前后端联调→用户验收”纵向闭环，未完成可视化验收不得进入下一个业务模块
  11. 🟪 决策者一次性确认5个或以上任务时，编码前必须全量审查此前所有前后端功能；每累计完成5个任务必须通过兼容性审查和全量测试并创建Git提交及附注标签
  12. HTTP 200/201 或页面可打开不等于功能通过；必须同时完成业务断言、浏览器 Console/Network 监控、边界/权限/失败恢复/幂等测试，所有情况通过且无未解释错误后才能标记完成
  13. 🟦 MCP全量边界验收是唯一的测试执行连续例外：在当前任务已获确认、本地服务、隔离测试数据和既定场景矩阵范围内，可连续执行所有MCP场景而不逐场景等待用户确认；修复、扩大范围、任务完成/状态更新、Git、远程操作和真实付费仍须用户确认
```

## 模型使用路由与功能选择整改计划（已审核，按任务执行）

> 本计划对应 `PRD_V5.0.md` 第13.4节，是新增整改任务。审核通过前不编码、不标记任务完成、不修改既有任务统计；整改不追溯性否定此前已完成并验收的功能，历史差异通过本计划或独立补漏任务兼容处理。审核通过后仍须一次只执行一个任务，并按“后端模型/服务 → REST API → 对应前端 → 真实本地API联调 → 用户验收”闭环。

### 整改目标与统一规则

- 模型选择优先级统一为：本次操作临时选择 → 功能已保存绑定 → 平台全局默认 → 明确启用的备用模型 → 用户明确选择的确定性基线。

- 全局默认模型必须经过能力过滤；不支持视觉、结构化输出或长上下文的模型不得被强行用于对应功能。
- “未配置”“能力不匹配”“供应商/密钥/网络调用失败”“使用备用模型”“使用确定性基线”必须分别展示并写入审计；默认不允许静默降级。
- 每个功能都提供“继承全局”选项，并展示最终生效的供应商、模型、能力和来源；临时选择不覆盖已保存配置。
- 每个任务完成后执行专项测试和全量/集成测试，更新 `PROJECT_STATUS.md`；发现历史遗漏、权限、兼容性或状态不一致时先记录影响和整改顺序。

## 🟩 阶段24：RAG 二阶段——知识增强检索与智能体引用

> 本阶段是下一阶段的规划草案，需决策者审核后再编码。它用于补齐历史 T108（LlamaIndex 适配）和 T025（pgvector/关键词混合检索）的架构差异，不追溯性否定已验收的知识库 CRUD、解析和基础检索能力。阶段内仍必须逐任务执行，并遵守“后端能力 → REST API → 对应前端 → 真实本地 API 联调 → 用户验收”的纵向闭环。

### 阶段目标与明确边界

- 目标：把现有知识库基础能力升级为可解释、可评估、可回退、严格项目隔离的 RAG 能力。
- 数据真理源：Django ORM、PostgreSQL、审核状态和项目权限；LlamaIndex 只能作为文档节点、索引和检索适配层。
- 检索底座：PostgreSQL 16 + pgvector + PostgreSQL 全文关键词检索；不新增独立向量数据库。
- 默认产品路径：审核通过 → 建立索引 → 混合召回 → 去重/融合 → 可选重排序 → 引用上下文 → 智能体回答。
- 明确不做：本阶段不引入 MCP、多智能体框架、第二套主编排器、自动训练模型或无审计的自动知识沉淀。

### 各业务域独立总运行与动态链路强制门禁（适用于 T169B、T170-T173、T173A 及 T178-T184）

本节是 PRD 11.6.3.1 的可执行验收门禁，覆盖需求文档、接口文档/OpenAPI、UI 流程、App 交互资料、性能目标/方案以及未来新增测试领域。共享的是运行协议、状态机、快照、血缘和进度投影，不共享一个混合所有领域节点的默认总运行。需求分析、接口自动化、UI 自动化、App 自动化和性能测试必须各自从自己的功能页面创建独立的 `workflow_key`/`domain` 父级运行；只有用户明确发起跨域编排时，才允许通过显式上层运行或父子运行关系关联。

1. **业务域先规划后执行：** 用户从某一业务域页面发起跨节点操作时，只能创建或幂等复用该业务域的父级运行。运行开始前必须解析本域输入类型和完整 DAG，冻结资料/环境版本、来源指纹、Skill 链/配置/模型/提示词/执行器快照、节点顺序、依赖、人工门禁和失败策略；计划不完整或关联不唯一时必须在首个业务节点前阻断。
2. **节点关联唯一：** 每个节点必须有稳定 `node_id`，绑定当前业务域唯一 Skill 与执行器版本、输入产物版本和输出产物版本；下游只能消费本父级运行内通过 Schema、来源证据、领域执行器和质量校验的精确产物，禁止查询最新记录、跨业务域拼接、按标题猜测或用旧结果补齐。
3. **领域边界明确：** 接口自动化节点只能进入接口自动化父级运行，UI、App、性能和需求分析同理；不同域不能共享当前运行的节点集合或百分比分母。不适用节点必须标为 `not_applicable` 并记录原因，不能静默跳过；跨域来源必须通过明确的版本化产物和父子运行关系传递。
4. **完成顺序不可倒置：** 业务产物、证据和版本指纹持久化成功后，节点才能完成；当前业务域所有适用必需节点完成、人工门禁通过且父级输出快照成功后，父级才能完成。任何失败、超时、网络/供应商/设备/浏览器异常、权限/Schema/质量失败、人工驳回或产物缺失都必须停止受影响下游并保留错误，不能显示成功或 100%。
5. **权威结果不可混用：** 同一业务域父级运行内只能产生一个当前权威结果版本；重新执行必须是新尝试/新父级并保留旧证据，不能覆盖或拼接旧运行。上游资料、环境、Skill、执行器、配置或需求版本变化时，受影响下游必须失效或回到人工门禁。
6. **动态进度必须可证明：** 业务域工作台必须同时显示自己的总链路/分支、当前节点/总节点、当前 Skill/版本、领域执行器、真实阶段提示、运行 ID、排队/执行/复用/不适用/人工等待/阻断/失败/取消/重试/恢复状态；百分比只能来自本业务域本次运行适用节点的已完成权重和可靠工作量，其他业务域运行和复用来源不得计入。
7. **入口一致且可恢复：** 页面、REST、Celery、智能体和 MCP 必须复用同一业务域父级运行、计划解析、状态机和进度投影；重复点击和重投恢复同一幂等运行，刷新读取持久化快照，关闭弹窗不取消运行，显式取消必须等待 Worker 确认。

未通过以上任一门禁时，只能标记为阻断/待整改，不能标记“该业务域工作流完成”，不能把结果作为下游唯一输入，也不能用静态流程图、忙碌弹窗或 Skill 名称回显替代真实链路证据。验收必须覆盖需求、接口、UI、App、性能的代表性工作流，并覆盖正常、空数据、字段/Schema 错误、401/403、权限边界、重复提交、上游变更、旧数据兼容、节点失败、重试、取消、刷新恢复、环境/设备不可用和跨入口一致性。

#### 自动评审结论与默认决策

经本次交叉审查，原有补充已经覆盖“独立业务域父级运行、节点唯一关联、动态进度、失败阻断、跨域隔离”的主干，但此前没有把进程级故障、外部副作用、权限中途变化、事件乱序、成本熔断、模型不确定性和旧数据兼容写成可验收门禁。本矩阵已补齐这些遗漏。

在没有额外产品决策前，后续开发采用以下安全默认值：

- 默认一个业务域一个父级运行；跨域默认禁止，必须由用户明确选择并建立显式父子关系。
- 默认失败闭环（fail closed）：无法确认输入、Skill、环境、来源、权限、产物或下游关联时阻断，不猜测、不静默降级、不用旧结果补齐。
- 默认重试不跨越数据边界：输入/配置/Skill/环境未变才允许节点级重试；发生变化就创建新运行。
- 默认外部写操作、App 操作、生产环境和性能负载需要范围、授权、预算和清理策略；没有证据就不能执行。
- 默认进度宁可停在“等待确认/阻断/未知”，也不能为了用户看到 100% 而估算或平滑补齐。
- 默认模型冲突保留差异并进入人工判断；平台只保证运行结果唯一可追溯，不把模型结果宣称为客观唯一真理。

仍需在对应业务域任务中明确的不是通用底座，而是领域参数：节点清单、输入/输出 Schema、适用性规则、权重、可重试边界、外部副作用清理方式、人工门禁点和最终质量阈值。未明确前，该业务域只能进入设计/阻断状态，不能标记完成。

### 🟫 T155C 需求分析五轮递进复核与覆盖补全（代码完成，真实验收受模型输出校验阻断）

#### 任务目标

#### 五轮任务边界

| 轮次 | 本轮必须完成 | 本轮不得做 |
| ---- | ------------ | ----------- |
