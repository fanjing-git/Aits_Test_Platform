# AITS 项目契约执行补充（强制）

生效日期：2026-09-04

本文件是核心开发契约的执行补充，优先级覆盖整个项目：需求分析、任务拆分、后端、前端、联调、测试、验收、修复、重构、Git 和会话续接都必须受核心契约约束。任何临时需求、效率目标或已有代码状态都不能绕过契约；冲突时以契约为准。

## 契约文档链覆盖门禁（强制）

项目当前有效的规则不是某一份文件，而是完整文档链：根目录 `AGENTS.md`、`doc/AGENTS.md`、本文件、核心开发契约、`SESSION_START_AUDIT.md`、`PROJECT_STATUS.md`、`TASKS_V5.0.md`、`PRD_V5.0.md`、`TECH_ARCH_V5.0.md`、`.env.example`，以及在核心契约中登记的专项方案（当前包括 LLM 代理兼容方案和模型调用全链路整改计划）。

新需求、新任务、新技术边界、新专项计划、新环境/部署约束必须同时登记到对应的需求、架构、任务和状态文档；只写在某一份文档、截图、聊天消息或代码注释中，不得进入实现。新增有效文档必须加入核心契约的引用表和启动审计范围；历史/归档文档必须明确标识，不得与当前规则混用。

启动审计必须确认上述文档存在、引用关系一致、任务统计和依赖同步、状态记录没有把未测试或未验收内容标成完成。文档链未闭合时，暂停编码并先完成文档整改。

## 文档一致性强制门禁

1. 所有功能必须严格依据 `PRD_V5.0.md` 开发；PRD 是功能范围、业务规则和验收口径的唯一需求真理源。
2. 所有开发必须执行 `TASKS_V5.0.md` 中对应的任务和功能节点；未登记、未满足依赖或跨任务顺便开发的内容不得实现。
3. 所有开发技术必须严格依据 `TECH_ARCH_V5.0.md`；模块边界、接口分层、数据模型和框架选型与技术架构不一致时不得开发。
4. 本门禁约束生效后的新增开发、缺陷修复、重构、接口调整和整改实现；约束生效前已经完成并通过验收的功能不因本条被追溯性判定为不合格，既有能力保持可用，文档差异登记为独立整改任务。
5. 约束生效后的实现未按上述三个文档执行，一律判定为不合格，不得以功能已存在、测试通过或用户可操作为豁免；必须停止、记录影响、整改并重新验证后才能继续。

## 硬门禁

1. 启动新会话必须读取项目状态、任务清单、PRD、技术架构、核心契约并完成启动审计。
2. 每个任务必须按后端能力、REST API、对应前端、真实本地 API 联调、用户验收闭环；完成两轮测试后停止等待确认。
3. 后端每完成一个可操作功能，必须紧接着完成对应前端入口和严格调试流程；前端未完成或未通过真实代理联调，不得进入下一个后端业务功能。
4. 发现历史违规、遗漏、兼容性问题、权限问题、交互问题、未解释失败或记录不一致时，必须先报告影响和整改顺序，暂停后续任务。
5. 决策者一次确认 5 个或以上任务时，编码前必须全历史审查；每累计完成 5 个任务必须完成 Git 兼容性审查、专项测试、全量回归、迁移检查、前端构建、关键端到端验证、提交和附注标签。
6. 没有可信基线时，首个批次前必须建立 `baseline/YYYYMMDD-pre-batch`；检查点使用 `checkpoint/YYYYMMDD-任务范围`。
7. Git 推送属于外部变更，只有决策者明确发出“推送 Git”指令时才执行；本地提交和标签按检查点门禁执行。
8. 任何违反门禁的实现均视为不合格，必须重新审查、整改、测试并记录，不能以“功能已经存在”或“测试通过”豁免。
9. 长输入或长结构化输出不得通过无限提高单次 token 上限解决；必须有预算规划、可追踪分段、续接/截断处理、幂等合并、部分完成状态和单段恢复，并验证所有受影响调用方。

## HTTP 200 非通过门禁（强制）

HTTP 状态码只表示传输层结果，`200`、`201` 或页面能够打开都不代表业务功能通过。任何任务不得以单个接口返回 2xx、Postman 成功、Shell 成功或浏览器页面可加载作为完成依据。

判定功能通过必须同时满足：

1. REST 响应结构、业务状态、数据持久化/副作用和权限结果符合契约；不能只检查状态码。
2. 前端真实工作台完成加载、空数据、成功、字段错误、401、403、404/409、5xx、超时、网络中断、能力不匹配、重复提交、取消/重试和旧数据兼容验证。
3. 浏览器验证期间必须监控 Console 和 Network：不得存在未解释的 `error`、未处理 Promise rejection、前端运行时异常、关键请求失败、错误重试风暴、响应解析异常或状态不同步。已知第三方无害警告必须单独记录并证明不影响功能，不能笼统忽略控制台输出。
4. 必须验证失败后的恢复路径：页面状态可恢复、按钮不会重复提交、重试边界明确、服务端与前端状态一致、不会产生重复数据或隐式副作用。
5. 必须完成后端专项测试、调用方/共享链路回归、前端构建和真实本地 API 浏览器联调；任一边界未覆盖、控制台存在未解释错误或结果与响应语义不一致，任务不得标记完成。

完成报告必须同时列出 HTTP 状态码、业务结果、浏览器 Console/Network 观察结果、边界场景矩阵和未覆盖风险。只有“各种情况测试通过且无未解释错误”才允许更新任务状态或创建 Git 检查点。

## MCP 浏览器全量多维度验证门禁（强制）

本门禁适用于每一次新开发功能、缺陷修复、问题整改、接口调整和影响用户行为的重构；不得因为改动规模小、后端测试已通过或页面“看起来正常”而豁免。

1. 必须使用可用的 Codex MCP/Playwright MCP，在真实本地服务和真实登录态下执行浏览器验证；只读取页面快照或只确认一个成功状态，不构成测试通过。
2. 必须针对变更功能及其受影响调用链执行多维度矩阵：页面入口、加载中、空数据、正常成功、字段错误、401、403、404/409、5xx、超时、网络中断、能力不匹配、重复提交、取消、重试、旧数据/旧接口兼容、权限边界和失败后恢复。场景确实不适用时，必须记录“不适用原因”和替代证据。
3. 每个场景必须实际操作并同时核对：用户可见结果、请求/响应状态和业务内容、数据持久化或副作用、页面回读结果、按钮/状态是否可恢复，以及浏览器 Console/Network 是否存在未解释错误或失败请求。
4. MCP 验证必须覆盖成功链路和异常链路，不能用单元测试、Shell、Postman、Django Admin、接口 2xx 或静态截图替代；后端测试只能作为链路证据的一部分。
5. 需要临时数据时必须使用唯一标识、限制范围、验证后精确清理，并在报告中记录创建与清理结果；涉及真实计费、外部发送或生产数据仍须单独取得明确授权，不得因 MCP 门禁自动扩大外部副作用。
6. MCP 不可用、浏览器无法连接、关键场景无法执行或存在未解释错误时，任务状态必须保持“未完成/真实验收阻断”，先报告阻断原因和整改顺序，禁止标记完成、更新任务状态或创建 Git 检查点。
7. 完成报告必须附 MCP 场景矩阵和证据：操作路径、预期、实际页面结果、API/Network、Console、持久化回读、清理结果和未覆盖风险。每个新功能或问题修复均须独立记录，不得以其他任务的 MCP 记录代替。

### MCP 全量边界验收的连续执行例外（仅限测试动作）

- “等待用户确认”仍适用于任务启动、方案调整、编码、缺陷修复、任务切换、完成认定、状态更新、Git 操作、远程部署和任何外部副作用。
- 仅当当前任务已经获得用户确认、目标为本地服务、使用隔离测试数据且全量场景矩阵已经确定时，MCP 可以在同一轮边界验收中连续执行全部测试场景，不必在每个场景之间暂停请求人工确认。
- 该例外只授权测试人员执行浏览器操作、输入测试数据、读取结果、核对请求/响应、检查副作用、清理临时数据和记录证据；不授权写代码、修改配置/数据库、修复缺陷、扩大测试范围、切换任务、更新任务完成状态、创建/推送 Git、远程部署、生产数据操作、外部发送或真实付费调用。
- 发现失败时，可以继续执行剩余的不依赖失败前置的测试并完整记录证据；需要修改代码、配置、数据结构或测试范围时，必须停止并向用户报告，等待确认后再处理。
- MCP 连续跑完全部场景不等于用户已经验收通过。仍必须输出独立验收报告，明确通过、失败、阻断和未覆盖项，并等待用户确认后才能标记任务完成、更新状态或进入下一任务。
