```
2. 涉及新的技术组件或框架的引入
3. 涉及数据库结构变更（≥3张表或复杂关系）
4. 涉及核心业务流程的完整实现

8. 代码量预估超过500行
9. 需要超过3个开发步骤
10. 涉及安全敏感操作
```

### 2.2 复杂功能开发流程

```
触发复杂功能判定
    ↓
阶段一：独立分析与计划设计
  1. 独立分析需求（基于正常社会思维）
  2. 设计开发计划（节点拆分+依赖关系）
  3. 设计节点计划（小模块拆分+完成标准）
  4. 输出计划文档 → 等待用户手动确认
    ↓ 用户确认
阶段二：逐节点开发
  5. 拆分小模块
  6. 逐模块开发
  7. 每模块完成即自测
  8. 所有模块完成后节点内联合自测
  9. 输出节点完成报告 → 等待用户确认
    ↓ 用户确认
阶段三：整体联合测试
  10. 所有节点完成后全功能联合自测
  11. 输出完整测试报告 → 等待用户确认
```

## 🟧 11.【V5.1 已人工验收】新增框架治理契约

### 🟧 11.1 单一主编排权

🟧 LangGraph是平台唯一主编排器和任务状态真理源。LlamaIndex、CrewAI、AutoGen、Microsoft Agent Framework及其他框架不得直接控制平台任务生命周期、Celery最终状态或绕过LangGraph条件路由。

🟧 业务Service禁止直接导入可选多智能体框架；必须通过AgentRuntimeAdapter调用。默认使用单智能体，只有职责可清晰拆分、收益高于额外成本且用户确认后才可启用多智能体。

### 🟧 11.2 LlamaIndex边界

- 🟧 仅用于文档连接、节点化、索引和检索适配。
- 🟧 Django ORM、PostgreSQL/pgvector、项目隔离和知识审核状态仍是数据真理源。
- 🟧 必须提供不依赖LlamaIndex云服务的本地路径以及安全降级。
- 🟧 检索前后均必须执行项目、用户、审核状态和敏感数据过滤。

### 🟧 11.3 MCP安全红线

- 🟧 MCP Server默认不受信任；接入前登记来源、版本、负责人、传输、能力和权限。
- 🟧 所有Tools/Resources/Prompts必须经过Schema校验、RBAC、项目隔离、超时、输出脱敏和审计。
- 🟧 防范工具描述投毒、间接提示词注入、同名工具替换、权限提升和跨Server数据外泄。
- 🟧 涉及写入、删除、代码执行、外部发送、生产环境或敏感数据时必须触发HITL；超时默认拒绝。
- 🟧 测试必须使用本地Fake MCP Server或Mock，禁止调用未知公共Server。

### 🟧 11.4 HITL与开发确认隔离

🟧 产品运行时HITL用于最终用户审批智能体操作；本契约第2、3节的人工确认用于约束AI开发过程。两套确认不得合并、替代或自动继承。

- 🟧 HITL checkpoint必须持久化最小必要状态，恢复时重新校验身份、角色、项目和工具权限。
- 🟧 节点恢复必须幂等；审批前已产生的外部副作用不得重复执行。
- 🟧 审批界面必须展示对象、影响、数据去向、成本、可撤销性和超时结果。

### 🟧 11.5 多框架依赖与测试门禁

- 🟧 不得因为技术架构列出框架而一次性安装全部依赖；必须等对应TASK开始并由用户确认版本。
- 🟧 AutoGen进入维护模式时不得作为新生产核心；须与其后继方案共同评估后再决策。
- 🟧 跨框架测试必须覆盖状态映射、取消、超时、重试、降级、费用上限、权限一致性和追踪关联。
- 🟧 可选框架关闭时，原LangGraph路径必须保持零行为差异。
- 🟧 所有框架调用在测试中使用Mock，禁止真实计费；多智能体测试额外验证调用次数和成本上限。


## 🟦 12.【V5.2 已人工确认】纵向交付与决策者验收契约

### 🟦 12.1 业务闭环顺序

🟦 每个可独立验收的业务模块必须按照“后端模型/服务 → REST API → 对应平台前端 → 真实API联调 → 用户验收”的顺序交付。禁止把已具备API的用户功能长期留到项目末期集中补页面。

- 🟦 REST API完成后，下一任务必须是该模块的前端闭环任务；用户验收前不得进入下一个业务模块。
- 🟦 Shell、Postman、自动化测试和Django Admin只能作为开发验证证据，不能替代智能体平台前端的产品验收。
- 🟦 没有独立用户操作价值的底层小任务可以在一个业务模块内按依赖连续推进，但仍须遵守逐任务确认和两轮测试规则。

### 🟦 12.2 人类使用与社会认知门禁

- 🟦 页面必须让目标角色理解“我在哪里、当前发生什么、操作会影响谁、是否可撤销、失败后怎么办”。
- 🟦 技术概念必须转化为用户可理解的名称和说明；不得把数据库字段、异常堆栈或内部状态直接当成产品文案。
- 🟦 高风险、外发、计费、删除和权限变更操作必须明确说明影响并提供相称确认；普通低风险操作不得滥用弹窗造成确认疲劳。
- 🟦 功能入口、可见性和可操作性必须与角色权限一致，不能展示注定失败的操作诱导用户。

### 🟦 12.3 前后端联调完成标准

- 🟦 前端必须连接真实本地API，覆盖加载、空数据、成功、字段错误、401、403和服务失败状态。
- 🟦 每个闭环必须通过后端专项测试、前端构建或组件测试以及至少一条关键端到端用户路径。
- 🟦 完成报告必须给出用户可访问地址、工作台入口、验收账号/前置条件和操作路径，便于决策者立即验收。
- 🟦 前端验收发现的API或数据结构问题必须在当前闭环修复，不得以“后续统一调整”为由积累返工。

### 🟪 12.4【V5.3 已由决策者确认】五任务批量确认触发全历史严格审查

当决策者一次性确认连续开发 **5个或以上任务** 时，在开始该批次编码前，AI Coding开发者必须对此前所有已开发功能执行一次全量严格审查，不得只检查本批次依赖或最近修改的文件。

- 🟪 审查范围必须同时包含前端、后端、数据库模型与迁移、权限与安全、任务依赖、配置、真实API联调、用户操作路径和现有测试证据。
- 🟪 必须以正常人的使用思维和社会认知规则重新判断：目标角色是否理解功能、操作路径是否自然、权限与影响是否符合职责、异常反馈是否可行动、危险操作是否有相称保护。
- 🟪 必须检查已实现功能与PRD、技术架构、任务清单和产品契约的一致性，不得因为代码已有测试或曾经标记完成而免审。
- 🟪 如发现遗漏、逻辑问题、交互问题、安全问题或记录不一致，必须先向决策者报告问题、影响、风险和建议处理顺序，并暂停批量开发，等待决策者决定先修复还是调整批次。
- 🟪 全历史审查结论、发现的问题、处理决定和测试结果必须写入`PROJECT_STATUS.md`，供后续会话继续复核。

### 🟪 12.5【V5.3 已由决策者确认】Git兼容性审查、五任务检查点与标签

在一次确认5个或以上任务的批量开发中，每累计完成 **5个任务**，必须执行一次Git检查点流程；不足5个的批次尾项在该批次验收完成时也必须形成独立检查点。

1. 提交前先审查完整Git变更，逐项确认新代码没有污染、覆盖或破坏此前已完成的前端、后端、数据结构、接口契约、权限逻辑和用户操作链路。
2. 严格验证新旧代码兼容性，包括API请求/响应、数据库迁移、配置与环境变量、路由与导航、权限边界、异常处理、依赖版本及已有数据兼容。
3. 执行与风险相称的专项测试、后端全量回归、迁移一致性检查、前端构建，以及已完成核心业务的关键端到端路径；测试失败或存在未解释警告时禁止提交检查点。
4. 审查和测试通过后创建一次范围明确的Git提交，并创建附注标签，格式为`checkpoint/YYYYMMDD-任务范围`；标签说明必须记录任务范围、审查结论和测试摘要。
5. 若仓库尚无可信基线提交，进入首个批量开发前必须先审查当前全部代码并创建`baseline/YYYYMMDD-pre-batch`附注标签，使后续检查点能够可靠比较。
6. 提交或标签创建完成后必须向决策者报告提交哈希、标签、包含任务、兼容性结论和测试结果。标签只提供可追溯恢复点；任何回滚仍须由决策者明确授权，禁止AI自行回滚。

上述检查点不能替代逐任务的两轮测试、前端闭环和用户验收；它是防止后续代码污染既有完整功能的额外强制门禁。
