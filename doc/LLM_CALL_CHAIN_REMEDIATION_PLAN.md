# AITS 模型调用全链路整改开发计划

状态：整改计划执行中。T151-T159 已完成，T155A 已完成共享长结构化运行时，未修改远程部署。

日期：2026-09-09（Asia/Shanghai）

## 1. 整改目标

只要平台启用了一个模型配置，所有已经对用户开放且明确依赖大模型的功能，都必须使用同一套可追踪的模型运行时和实际生效路由完成调用。连接测试通过不能再被当作深度分析、五轮用例生成或评审已经通过的证据。

本计划必须形成以下闭环：

```text
模型配置/密钥
  → 供应商能力与协议适配
  → 全局/功能/本次路由解析
  → 结构化调用与超时/重试/费用边界
  → 业务服务持久化
  → REST 错误与执行轨迹
  → 前端生效模型、阶段、失败原因和重试
  → Mock 回归 + 真实短调用验收
```

## 2. 审计结论与当前根因

### 2.1 已复现根因

- 本地全局路由当前指向通义 `qwen3.8-max`；需求分析、用例生成、用例评审继承该路由，未配置备用模型。
- 模型连接测试只发送很短的 `Reply OK`，通义探测请求带 `enable_thinking=false`，因此测试通过。
- 结构化业务调用走 `apps/requirement_analysis/llm_adapter.py`，通义请求没有沿用 `enable_thinking=false`，还携带更大的需求证据和 JSON 约束；同一份 8771 字符、271 条证据的真实调用超时。
- 对同一请求补充 `enable_thinking=false` 后返回 HTTP 200，证明本次故障不是 Key、路由地址或网络连通性，而是业务运行时与连接探测协议不一致。

### 2.2 全链路缺口

| 链路 | 当前情况 | 风险 | 整改结论 |
| --- | --- | --- | --- |
| 连接测试 | 与业务调用使用不同参数和协议 | 连接测试通过但真实功能失败 | 必须提供与业务场景一致的能力探测 |
| 需求分析 | 共享 OpenAI-compatible 运行时，通义参数缺失；失败后前端仍显示分析中 | P0 | 纳入本次整改 |
| 用例生成 | 五轮共用同一运行时；任意一轮失败即可能整链失败 | P0 | 纳入本次整改 |
| 用例评审 | 五轮复用同一运行时，失败原因和轮次不够清晰 | P0 | 纳入本次整改 |
| 截图/视觉 | 能力路由存在，但视觉协议和真实验收边界仍需逐供应商确认 | P0 | 纳入本次整改 |
| 智能体 | 页面可绑定模型，但 `AgentGraph` 当前主要执行确定性节点，未形成真实模型调用闭环 | P1 | 纳入计划，不能继续宣称已接入 |
| 知识库 Embedding | 当前使用 `HashVectorizer`，不是配置的 Embedding 模型 | P1/RAG | 本计划先完成能力边界和显式状态；生产 RAG 接入仍依赖阶段24任务 |
| 联合识别 | 当前为确定性业务服务，不应伪装成模型调用 | — | 保持明确标识，不强行接入模型 |

## 3. 设计原则与范围边界

### 3.1 必须做到

1. 所有模型调用先解析同一个 `ResolvedModelRoute`，不得由业务模块自行查询“任意活动模型”。
2. 供应商协议、请求参数、响应解析、错误分类和超时策略集中在运行时适配层。
3. 连接测试必须区分网络预检、目录可见、文本结构化、视觉结构化和 Embedding 能力；“目录存在”不能标记为“业务可用”。
4. 失败时必须记录脱敏的供应商、模型、功能、阶段、错误码、是否已产生费用和可重试性；禁止记录 Key、Authorization、原始项目内容。
5. 明确配置的路由失败时不得偷偷切换其他供应商。备用模型只有在策略允许时才能使用。
6. 每个前端操作都要显示实际生效模型、调用阶段、成功/失败、重试边界和服务端错误原因。

### 3.2 明确不在本次 P0 偷塞的内容

- 不把连接测试改成定时收费健康检查。
- 不因模型失败自动生成确定性结果并伪装成模型结果。
- 不把确定性的联合识别、OCR 基线或本地 HashVectorizer 宣称为大模型能力。
- 不把 RAG 二期完整实现并入本整改；Embedding 的正式供应商接入继续遵守阶段24的维度、成本和迁移计划。
- 不更新远程部署，除非收到明确的“更新远程部署”指令。

## 4. 分阶段开发顺序

### 阶段 A：运行时与供应商能力统一（T151-T154）

先消除“连接测试通过、业务调用失败”的协议分叉，再开放业务修复。

### 阶段 B：共享长结构化运行时与业务纵向闭环（T155A、T155-T157、T155B）

先完成共享长输入/长结构化结果分段运行时，再按“后端服务 → REST → 前端 → 真实本地 API”分别完成需求分析、用例生成/评审和智能体调用。不能把增加单次 token 上限当作长内容闭环。

T155B 补充需求分析结果的可重复性与覆盖完整性：结构合法不等于覆盖完整，必须记录源/证据/模型/Prompt/Schema 指纹、分段遗漏与截断、完整性状态和重复分析差异；低覆盖结果不得静默替代已验证结果。

### 阶段 C：能力边界、目录与可观测性（T158-T159、T161）

明确 Embedding/RAG 边界、官方模型目录和选择器状态，补齐调用轨迹和成本信息；最后由 T160 完成全量回归与一次授权真实验收。

## 6. 每个任务的强制门禁

每个任务必须独立完成以下步骤，不能跨任务顺便修改：

1. 编码前输出该任务的影响范围、依赖、输入输出契约和回滚边界。
2. 先完成后端 Service/运行时，再完成 REST，再完成对应前端入口。
3. 第一轮：任务专项测试，使用 Mock 覆盖正常、空数据、字段错误、401、403、服务失败和能力不匹配。
4. 第二轮：全量/集成测试、迁移检查、前端构建和真实本地 API 联调。
5. 发生任何失败，修复后两轮重新执行，不得用旧测试结果替代。
6. 每个任务更新 `PROJECT_STATUS.md`，列出修改文件、测试、影响矩阵、遗留问题和下一任务；报告后暂停等待确认。
7. T160 才能汇总一次明确授权的真实供应商短调用；自动化测试不得访问真实供应商。
8. T161 必须严格区分“官网目录支持”“当前凭据可访问”和“当前端点实际可调用”；不得为自定义、本地或无公开目录的 Provider 生成虚假官网模型清单。
9. HTTP 200/201 只代表传输层成功；每个任务必须同时验证业务语义、持久化/副作用、浏览器 Console/Network、边界场景、权限、失败恢复和幂等性。存在未解释的控制台错误、关键网络错误或未覆盖边界时不得标记完成。
10. T155A 必须先于 T155/T155B/T156 的长内容实现完成；单次 `max_tokens` 提高、供应商返回 200 或解析出一份 JSON，均不能替代分段计划、续接、确定性合并、部分状态和调用方回归。
