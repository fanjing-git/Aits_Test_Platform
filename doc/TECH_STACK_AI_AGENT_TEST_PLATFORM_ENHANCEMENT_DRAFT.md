# AI 智能体测试平台增强版技术栈与架构草案（预存）

> 文档状态：预存技术方案草案，仅供后续评审。
>
> 本文件独立于现有 `TECH_ARCH_V5.0.md`，不属于当前正式技术方案，不授权安装依赖、修改架构或开始开发。后续实施前必须完成兼容性、成本、安全和运维评审。

## 1. 总体原则

1. 复用现有 Django、DRF、Celery、Redis、PostgreSQL、Vue 和 LangGraph 基础，不另起一套主编排器。
2. 平台编排智能体与被测智能体必须使用隔离的身份、网络、数据和生命周期。
3. 测试结果以执行轨迹和版本化数据为依据，不以最终文本单独作为事实。
4. 评估引擎支持规则、模型和人工三类评估器，并保留评估证据。
5. 所有外部调用、工具调用和高风险操作经过权限、预算、超时和审计门禁。
6. 任何记忆、知识和轨迹都必须有作用域，禁止跨项目或跨用户隐式共享。

## 2. 建议逻辑架构

```text
测试工作台 / CI / 定时任务
          ↓
测试计划与数据集服务
          ↓
Agent Test Orchestrator（测试编排）
          ↓
被测智能体适配器 ── 工具/MCP沙箱
          │          ├─ Mock工具
          │          ├─ 故障注入
          │          └─ 权限与副作用隔离
          ↓
轨迹采集器 Trace Collector
          ↓
评估引擎 Evaluator
  ├─ 规则评估器
  ├─ 模型评估器
  ├─ 人工评估器
  └─ 安全/一致性/性能评估器
          ↓
回归基线、报告、发布门禁、线上监控
```

现有 LangGraph 继续负责平台自身的对话和任务编排；`Agent Test Orchestrator` 可以作为受控业务服务接入，不绕过统一权限和运行时。

## 3. 后端技术栈建议

| 层次 | 建议技术 | 作用 |
|---|---|---|
| Web/API | Python + Django + Django REST Framework | 配置、权限、数据集、执行和报告 API |
| 任务调度 | Celery + Redis | 批量、并发、定时、取消和恢复 |
| 主编排 | LangGraph | 平台智能体状态、路由、人工确认和恢复 |
| 数据库 | PostgreSQL | 业务数据、版本、轨迹索引、评估结果和审计 |
| 语义检索 | pgvector；必要时复用现有 RAG 服务 | 长期记忆、测试资产和轨迹检索 |
| HTTP 被测适配 | `httpx` 或现有受控请求层 | API、流式和超时控制 |
| 浏览器被测适配 | Playwright | Web/多轮交互和页面证据 |
| 结构化契约 | JSON Schema / Pydantic 风格校验 | 用例、轨迹、评估器输入输出校验 |
| 文件存储 | 受控对象存储或项目文件存储 | 数据集、截图、导出报告，带大小和权限限制 |
| 观测 | 现有调用记录；可评估 OpenTelemetry | trace、耗时、错误阶段和跨服务关联 |
| 指标 | PostgreSQL 初期；后续可接 Prometheus | 质量、延迟、成本、漂移和门禁指标 |
| 前端 | Vue 3 + JavaScript + 纯 CSS | 工作台、轨迹、报告、回归和治理页面 |

优先复用项目现有依赖。新增依赖必须单独完成版本锁定、漏洞审查、许可证审查和回滚方案。

## 4. 核心服务划分

### 4.1 AgentTargetService

负责被测智能体注册、版本、协议、凭据引用、能力声明和项目边界。平台不得将被测智能体配置混入自身 Agent 配置。

### 4.2 TestDatasetService

负责数据集、场景、变量、参考答案、期望工具调用、标签、版本和审核状态。数据集版本必须生成稳定指纹。

### 4.3 AgentTestExecutionService

负责执行计划、会话重置、并发、超时、取消、重试、幂等和状态持久化。每条用例都要关联目标版本、数据集版本和环境版本。

### 4.4 TraceCollector

统一采集消息、状态、工具、检索、记忆、评估和错误事件。原始敏感字段在采集前脱敏，普通用户只能看到其权限范围内的摘要和证据。

### 4.5 EvaluatorRuntime

采用统一评估器协议：

```json
{
  "evaluator_id": "tool_call_correctness_v1",
  "input": "trace_reference",
  "result": {
    "status": "passed",
    "score": 4.5,
    "confidence": 0.92,
    "evidence": ["trace-event-123"]
  }
}
```

评估器必须声明输入、输出、版本、成本、超时和失败策略；评估器失败不能伪造为通过。

### 4.6 RegressionService

负责基线选择、版本对比、阈值、差异分类、发布门禁和报告。模型、Prompt、工具、知识库和记忆版本都属于可比较对象。

### 4.7 MemoryService / ContextAssembler

二期记忆能力统一由记忆服务提供，LangGraph 只负责调用和编排：

- `MemoryService`：保存、查询、更新、删除和审计记忆。
- `ContextAssembler`：按权限、优先级、时效、来源和上下文预算组装输入。
- 记忆作用域：session、project、user。
- 记忆状态：候选、已确认、已过期、已撤销、已删除。

测试执行必须支持固定记忆、空记忆、污染记忆和清空后重跑四种模式。

## 5. 工具与 MCP 测试沙箱

- 工具注册表声明名称、版本、输入 Schema、权限和副作用等级。
- 默认使用 Mock 或只读适配器。
- 对写操作、外部命令、文件、数据库和网络访问设置独立策略。
- 工具参数在调用前和调用后分别校验。
- 支持超时、断连、错误返回、延迟、空结果和恶意结果故障注入。
- 工具描述、返回值和检索内容都作为不可信输入处理。
- 沙箱必须能清理状态并保证重复执行幂等，不能把测试副作用带入真实环境。

## 6. 轨迹与数据模型建议

逻辑实体包括：

- `AgentTarget`：被测智能体及版本。
- `TestDataset` / `TestDatasetVersion`：测试数据集和版本。
- `TestScenario`：单轮、多轮、工具、RAG、记忆和安全场景。
- `AgentTestRun`：一次批量或回归执行。
- `AgentTestCaseResult`：单条用例结果。
- `TraceSession` / `TraceEvent`：会话轨迹和事件。
- `Evaluator` / `EvaluationResult`：评估器和评估结果。
- `RegressionBaseline` / `RegressionDiff`：基线和版本差异。
- `MemoryItem`：带作用域、来源、状态和权限的记忆。
- `SecurityFinding`：安全问题、证据、等级和整改状态。

所有实体至少需要项目 ID、创建者、版本/状态、审计字段和权限边界；大文本、截图和完整轨迹按保留策略存储，不能无限增长。

## 7. API 设计方向

建议 REST 资源：

- `/api/agent-targets/`
- `/api/test-datasets/`
- `/api/test-scenarios/`
- `/api/agent-test-runs/`
- `/api/agent-test-runs/{id}/execute/`
- `/api/agent-test-runs/{id}/cancel/`
- `/api/agent-test-runs/{id}/retry/`
- `/api/traces/{id}/`
- `/api/evaluators/`
- `/api/evaluations/`
- `/api/regressions/`
- `/api/security-findings/`
- `/api/memory-items/`

API 必须区分 401、403、404、409、422、超时、供应商失败、工具失败、评估失败和平台内部失败；不能只返回 HTTP 200 再把错误塞进普通文本。

## 8. 安全与合规架构

- 凭据使用现有加密配置和密钥管理边界，不写入数据库明文、前端或日志。
- 轨迹按项目、用户、角色和敏感字段进行过滤。
- 测试数据集支持保留期限、删除、导出审批和脱敏。
- 生产环境目标必须白名单校验，禁止利用重定向、代理或 DNS rebinding 绕过限制。
- 高风险工具和外部数据发送使用 HITL；超时默认拒绝。
- 评估 Prompt、被测输出和工具返回均按不可信内容处理，防止评估器被注入。
- 所有模型、工具、知识库和记忆版本写入测试指纹，确保结果可复现。

## 9. 分阶段技术实施建议

### P0

先实现被测智能体适配器、数据集、执行服务、基础轨迹、规则评估和报告；不依赖复杂多智能体框架。

### P1

接入工具/MCP 沙箱、RAG/记忆测试、模型评估、人工评估、红队样本、回归基线和发布门禁。

### P2

接入线上观测、漂移检测、CI/CD、自动采样、指标平台和企业级审计报表。

## 10. 主要技术风险

| 风险 | 处理方向 |
|---|---|
| LLM 评估不稳定 | 规则优先、模型评估辅助、人工抽样校准、多次评估保留差异 |
| 轨迹数据过大 | 分层存储、摘要、压缩、保留期限和敏感字段过滤 |
| 工具测试产生副作用 | Mock、沙箱、只读权限、幂等清理和人工确认 |
| 模型/Prompt 变化导致不可复现 | 保存完整版本指纹、参数和评估配置 |
| 成本失控 | 并发限制、预算预估、取消、分层模型和发布前确认 |
| 记忆跨项目泄漏 | 作用域过滤、权限二次校验、隔离键和专项负向测试 |
| 新框架引入维护成本 | 优先复用现有底座，任何新框架先做小范围兼容性评估 |
